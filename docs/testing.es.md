# Política de pruebas

[English](testing.md) | Español

Cómo prueba este repositorio, nivel por nivel, y las reglas que mantienen significativa una suite en verde. Los comandos viven en el [AGENTS.md](../AGENTS.md) raíz; las Agent Notes enlazadas llevan el fundamento.

## Niveles

- **Unit** (`pnpm run test`): vitest sobre los specs de paquetes y ejemplos en sus directorios `tests/**` más los specs de scripts del repositorio en `scripts/**/*.spec.ts`; las pruebas se quedan junto al área de código que ejercitan. Todo registro tiene una prueba de seguridad HMR (haz dispose del fiber que contribuye, afirma la limpieza). Prefiere los casos límite, los caminos de error, el orden de los eventos, las carreras de concurrencia y las pruebas permanentes para las regresiones de contrato (ver `packages/core/agent-loop/tests/contract-regressions.spec.ts`).
- **Gate de cobertura** (`pnpm run test:coverage`): la ejecución que hace de gate, 100% por archivo en `packages/*/*/src`. Una línea sin cubrir suele ser código muerto que el gate marca correctamente para eliminar, no una prueba que falte por añadir. La cobertura de líneas es necesaria, nunca suficiente — demuestra que las líneas se ejecutaron, no que la funcionalidad funciona tal como se entrega. El 100% por archivo en `packages/shell/pwsh-local/src` necesita un `pwsh` real: sin él, sus suites de ejecutor se omiten automáticamente y `vitest.config.ts` exime el archivo para que los hosts sin pwsh sigan en verde, mientras que los runners de CI traen pwsh y hacen cumplir la barra completa.
- **e2e con API real** (`pnpm run test:e2e`): pruebas con clave contra las APIs de provider en vivo — el modelo DeepSeek más pruebas de humo (smoke tests) específicas de cada provider que dependen de sus propias claves (`EXA_API_KEY`, `PERPLEXITY_API_KEY`, …); cada suite se omite automáticamente sin su clave para que la CI sin clave siga en verde ([Agent Note de e2e con API real](../.agents/notes/implemented/testing/2026-06-19-real-api-e2e-ci.es.md)).
- **Instantáneas** (`pnpm run test:snapshot`): las salidas esperadas sin clave cubren el comportamiento externo — los contratos de transporte y la presentación, mientras que los logs persistidos fijan el comportamiento ensamblado del backend. ACP arranca el ejemplo real del servidor de automatización, reproduce una sesión grabada y hace diff del JSON-RPC normalizado más el log re-persistido ([Agent Note de instantáneas ACP](../.agents/notes/implemented/testing/2026-06-19-acp-snapshot-tests.es.md)); los escenarios de backend headless arrancan su composición explícita de ejemplo mediante un driver de pruebas JSONL no exportado, mientras que `apps/cli` es dueño por separado de la aceptación del producto `dsh --profile headless`. Usa `pnpm run test:snapshot:record` cuando cambia un transcript (transcripción) de modelo y `pnpm run test:snapshot:refresh` cuando la entrada de replay sigue siendo válida; revisa cada diff de JSONL y de salida esperada. Un escenario ACP (`text-turn`) fija el contenido completo de system-prompt/schema de herramientas; otros fixtures (datos de prueba) lo tokenizan para que una edición altere solo una línea ([Agent Note de pinned-header](../.agents/notes/archived/testing/2026-07-06-pin-request-header-content-in-one-scenario.md)).
- **Instantáneas de navegador web** (`pnpm run test:web`; gate de PR en Linux obligatorio): Chromium compara la salida reproducida del navegador con `apps/web/tests/snapshots/`. La CI fuerza `DSH_SNAPSHOT=replay` en modo solo lectura, nunca escribe salidas esperadas; record/refresh se quedan en local y cada diff se revisa ([carril e2e web](../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.es.md), [decisión del gate de CI](../.agents/notes/implemented/testing/2026-07-30-web-browser-snapshot-ci-gate.es.md)). `test:web` [compila primero](../.agents/notes/implemented/bug-fix/2026-07-28-themed-scrollbars-and-reserved-gutter.es.md) para el CSS de los plugins.

Los fixtures de sesión conservan headers y payloads pero omiten los envoltorios de secuencia/tiempo del cuerpo. El replay los sintetiza; la persistencia en tiempo de ejecución no cambia. Los fixtures usan filas empaquetadas canónicas; [el migrador](../scripts/migrate-packed-session-fixtures.ts) reescribe los formatos antiguos.

## La política de pruebas con clave: aquí la inferencia es barata

Somos DeepSeek — no raciones las pruebas con API real. Una prueba sin clave demuestra el cableado; solo una ejecución con clave demuestra que el agent (agente) funciona contra un modelo real. Cubre prompts de escritura de archivos, conversaciones de varios turnos, uso de herramientas y cancelación a mitad de flujo. Lo más valioso son las **pruebas de humo** que arrancan el ejemplo real, envían un prompt y comprueban el mundo — capturan la clase «pruebas unitarias en verde, producto roto» que los mocks no pueden ([post-mortem 0001](postmortem/0001-acp-default-export-drops-inject.es.md)). Que las suites se omitan automáticamente mantiene desbloqueadas la CI sin secretos y las contribuciones sin clave; no es una señal de coste. Cada ejemplo entrega pruebas de humo sin clave y con clave ([examples/AGENTS.md](../examples/AGENTS.md)).

## Prefiere la implementación real a un mock

Haz mock solo de la frontera costosa o no determinista (adaptador LLM, red, reloj); mantén real todo lo que queda aguas abajo. Un sustituto hecho a mano demuestra que el puente mueve bytes, no que la herramienta que se entrega se comporta como se afirma. Las pruebas de llamadas de herramienta del puente usan el modelo mock controlado por script con la herramienta y el ejecutor reales: `makeBridgeHarness({ withBash: true })` enchufa `dsh-bash-local` y `dsh-tool-bash`, y luego ejecuta `echo`.

Las pruebas de recuperación separan por pasos los fallos previos y posteriores al chunk y demuestran que los chunks fallidos no producen ningún mensaje ni efecto secundario de herramienta. Cubren el agotamiento, la cancelación, la composición de políticas, la persistencia, el estado, los recuentos en el cable, los timeouts de inactividad que cierran el transporte y la composición del Loader que se entrega.

## Verifica el mundo, no el auto-informe

Una aserción e2e vuelve a ejecutar el comando o vuelve a leer el archivo desde fuera; una comprobación por palabra clave sobre la propia salida del agent deja pasar a un agent que hace trampa. Afirma que los archivos no tocados son idénticos byte a byte. Las pruebas e2e son dueñas de sus recursos: crea el harness en la prueba, haz dispose en `afterEach` (incluso ante fallo/reintento/timeout); los fixtures compartidos viven en un `tests/harness.ts` simple, nunca en otro `*.e2e.ts` (importar un spec vuelve a registrar su `describe` y duplica las llamadas reales a la API).

## Prueba la ruta de entrada real

- Los plugins visibles para el producto requieren una prueba de composición REAL no unitaria. Las suites de `ctx.plugin(...)` construidas a mano son insuficientes: arranca un `cordis.yml` solo de pruebas a través del Loader y de app/process, haz mock solo de los servicios externos o de las entradas no deterministas, y afirma la solicitud/log visible para el modelo, el estado duradero o la salida visible para el usuario. Mantén los opt-ins fuera de los valores por defecto que se entregan.
- Un guard solo protege si la regresión realmente lo hace fallar. Para un plugin sin `inject` (plugins de bundle/composición), una prueba de humo del Loader sigue en verde cuando un export por defecto reemplaza los exports con nombre requeridos — añade un `expect('default' in mod).toBe(false)` explícito más una aserción de ida y vuelta de `unwrapExports`, y demuéstralo: introduce la regresión, observa el rojo, revierte.
- «Ruta de entrada real» significa el artefacto publicado: el `bin` de un paquete ejecuta el `lib/bin.js` compilado con `node` plano, exponiendo fallos que tsx enmascara (carreras de conclusión, resolución de módulos, fallos de carga tragados). Lo mismo se aplica a las entradas de runtime que no son index (el hermano de hilo de trabajo `lib/worker.cjs`) y a los módulos singleton compartidos entre bundles (`packages/sdk/server/tests/built-scope-carrier.e2e.ts`). Mantén en verde las pruebas de humo del artefacto compilado (`packages/examples/*/tests/built-bin.e2e.ts`, `packages/code-runtime/code-runtime-worker-thread/tests/built-lib.e2e.ts`) y afirma que una config de verdad ausente sale con estado distinto de cero.

## Resolución de pruebas: solo el plano de código fuente

- Cada configuración de vitest apunta vite-tsconfig-paths a `tsconfig.base.json`; los imports desnudos de workspace resuelven a `src` ([disposición](development.es.md#typescript-project-layout)), nunca a través de los `exports` del paquete hasta el `lib/` compilado — los artefactos obsoletos que hay allí cargan una segunda copia de los módulos singleton. Los artefactos compilados se consumen solo de forma explícita: los subprocesos en modo `lib` y las pruebas de humo compiladas de más abajo.

## Modos de lanzamiento de subprocesos de prueba

- La CI y los carriles de prueba con compilado ejecutan cada subproceso de ejemplo o de configuración de Cordis desde el `lib/` compilado a través del lanzador compartido de doble modo. No escribas a mano `--import tsx` para estos subprocesos.
- Los fixtures de protocolo y de sistema operativo que no cargan Cordis ejecutan `.ts` borrables directamente con Node, sin tsx ni el mapa de rutas raíz.
- Solo una prueba cuyo objeto sea la resolución de rutas de código fuente puede seleccionar `src`; declara ese contrato en la prueba.

## Cuándo se requiere una prueba de instantáneas

Todo cambio no trivial visible para el modelo, el protocolo o las personas añade o actualiza un escenario sin clave en el mismo PR a través de la suite de instantáneas propietaria de un ejemplo ejecutable. Las pruebas de paquete, las aserciones e2e, las composiciones de mock/solo-pruebas y la justificación del PR no sustituyen al transcript ensamblado; extiende el harness cuando haga falta. Los escenarios de automatización ACP usan `examples/<name>/tests/snapshots/`, una tabla de escenarios sobre la fábrica de suites del [`dsh-acp-snapshot`](../packages/test-support/acp-snapshot/README.es.md) (`examples/acp-agent` es el principal); `examples/headless-agent` es dueño de las instantáneas JSONL de eventos canónicos internos y de los fixtures de replay. El escenario ACP `pwsh-tool-turn` arranca un `pwsh` real y se omite donde no existe. Los recorridos completados de terminal interactiva usan escenarios guiados por JSONL bajo `apps/cli/tests/snapshots/`; la presentación transitoria usa la matriz semántica local del paquete, con un caso PTY cuando cambian la entrada, la selección del Loader o el desmontaje de la terminal. Los recorridos de la GUI web renderizados en navegador usan `apps/web/tests/snapshots/`. Los dos SDK proyectan el agent loop (bucle del agente), el ciclo de vida de sesión y `SessionEventMap` de forma independiente, así que cambiar cualquiera de ellos actualiza ambos: `examples/jsonrpc-agent/tests/snapshots/` es dueño del cliente TypeScript; `scripts/snapshots/python-sdk-single-exe/` es dueño del cliente Python, que solo ejecuta el trabajo de CI `python-runtime` requerido. Los nuevos seams de capacidad, las variantes de ciclo de vida o las superficies de transcript nombran cada nivel de cobertura en el momento de la planificación y verifican que el harness puede expresarlo antes de la implementación.
