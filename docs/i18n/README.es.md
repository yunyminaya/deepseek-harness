# Documentación bilingüe

[English](README.md) | [中文](README.zh.md) | Español

La documentación de este repositorio la leen personas y agentes, tanto dentro como fuera de la empresa, por lo que cada documento dentro del alcance se mantiene en inglés y chino simplificado. Esta página define el contrato de emparejamiento, las verificaciones, el alcance y las exclusiones; [translation-rules.md](translation-rules.es.md) define cómo traducir; [terminology.md](terminology.es.md) es la fuente de verdad de la terminología. El trabajo rutinario de los agentes sigue la vía ligera de [docs/AGENTS.md](../AGENTS.md); el flujo de trabajo ampliado [.agents/skills/dsh-translate-docs/SKILL.md](../../.agents/skills/dsh-translate-docs/SKILL.md) solo está disponible mediante invocación explícita del usuario.

## El contrato de emparejamiento

- **Ambos idiomas tienen la misma autoridad.** Un documento puede redactarse y revisarse primero en cualquiera de los dos idiomas — una Agent Note escrita primero en chino es tan legítima como una escrita primero en inglés — y la contraparte se traduce a partir de él. Ningún archivo está por encima del otro; lo que los une es que deben decir lo mismo.
- **Un par son tres archivos hermanos.** El inglés `foo.md`, el chino `foo.zh.md` y un registro de coherencia `foo.i18n.yaml`, todos en el mismo directorio. Nada de directorios por idioma, ni un repositorio de traducción aparte, ni archivos bilingües intercalados. Los pares se fusionan completos: un PR nunca incorpora un idioma sin los otros dos archivos.
- **El registro de coherencia.** `foo.i18n.yaml` guarda el blob hash completo de git de cada lado en el último momento en que se confirmó que ambos decían lo mismo:

  ```yaml
  foo.md: 3f786850e387550fdab836ed7e6dc881de23001b
  foo.zh.md: 89e6c98d92887913cadf06b2adb97f26cde4849b
  ```

  Blob hashes, no hashes de commit, para que el registro sea computable para archivos editados en el mismo PR (`git hash-object foo.md`) y la coherencia sea una comparación de contenido pura. `--write` guarda esas instantáneas en la base de datos local de objetos de Git antes de registrarlas, incluidos los contenidos no confirmados del árbol de trabajo, y fija cada blob distinto almacenado bajo una ref con direccionamiento por contenido `refs/dsh/translation-pairing/snapshots/` para que la recolección de basura no pueda invalidar un puntero de recuperación registrado. Los hashes registrados recuperan por tanto el texto exacto confirmado por última vez de cualquiera de los dos lados, de modo que un par desincronizado se actualiza aplicando un parche mínimo a la contraparte contra el diff del lado editado — nunca retraduciendo archivos completos. El trabajo rutinario hace ese parche directamente; cuando el usuario invoca explícitamente el flujo de trabajo ampliado, `pnpm run gen-translation-brief <pair>` puede en su lugar ensamblar la actualización con la granularidad alineada de forma segura más estrecha y `--apply` puede insertar un cambio solo de vallas de código tras la validación estructural ([Agent Note de las actualizaciones breves](../../.agents/notes/implemented/process/2026-07-26-briefed-minimal-translation-updates.es.md)). Tras volver a alinear el par, `pnpm run verify-translation-pairing --write <pair>` vuelve a registrar ambos hashes; ese diff yaml es el acto revisable de confirmar la coherencia, que es por lo que `--write` exige nombrar los pares que confirmaste (`--write --all` es la forma explícita para todo el corpus).

  Cuando dos ramas contienen confirmaciones válidas del mismo par, el controlador de fusión de Git `dsh-translation-pairing` instalado compone un registro nuevo solo si la fusión de texto predeterminada de Git tiene éxito para ambos tripletes de blob del propietario registrados y el par fusionado conserva sus selectores de idioma obligatorios y su firma estructural. El archivo chino debe conservar su enlace de retorno al inglés; una fuente inglesa de autoría propia debe conservar su enlace al chino, mientras que una fuente inglesa generada en la lista está exenta. Cualquier estructura que el controlador no pueda verificar sigue siendo un conflicto ordinario; `pnpm run resolve-translation-pairing-conflicts` aplica la misma operación fail-closed a una fusión que ya se detuvo, añade al stage cada registro de emparejamiento seguro y termina con estado de error cuando quedan otros conflictos de emparejamiento. La [Agent Note de las fusiones de emparejamiento automáticas](../../.agents/notes/implemented/process/2026-08-08-automatic-translation-pairing-merges.es.md) es dueña del mecanismo y de las alternativas.
- **Selector de idioma.** El archivo chino siempre enlaza de vuelta inmediatamente después de su H1 con `[English](foo.md) | 中文`. Una fuente inglesa de autoría propia responde a su vez con `English | [中文](foo.zh.md)`; una fuente inglesa generada en la lista omite esa línea para permanecer byte a byte idéntica a la salida del generador. Un README publicado fuera de GitHub, como los metadatos de un proyecto en PyPI, puede usar la URL canónica `https://github.com/deepseek-ai/deepseek-harness/blob/master/<repository-path>` hacia la misma contraparte para que el selector siga resolviendo allí.
- **La estructura refleja a la contraparte.** Las profundidades y el orden de los encabezados, los tipos de lista, los inicios de listas ordenadas, el número de elementos de cada lista, el número de filas y columnas de las tablas, los destinos semánticos de los enlaces con sufijos de consulta/fragmento exactos y los bloques de código verbatim coinciden uno a uno en el par. Cuando un enlace de documento relativo apunta al corpus bilingüe activo, el lado inglés usa su ruta `.md` y el lado chino usa su ruta `.zh.md`. Una contraparte ausente en ese corpus es un error de completitud del par, no un recurso de reserva; los destinos fuera del corpus activo conservan la ruta de autoría. Consulta [translation-rules.md](translation-rules.es.md) para las reglas completas de preservación. Las compuertas Markdown existentes se aplican a los archivos `.zh.md` sin cambios (`verify-md-wrap`, `verify-md-links`).

## La compuerta: verify-translation-pairing

`pnpm run verify-translation-pairing` (parte de `doc-sync`, que los contribuyentes ejecutan localmente para los cambios de documentación y que la CI ejecuta de forma exhaustiva) hace cumplir el contrato mecánicamente:

1. Todo documento dentro del alcance tiene un par completo. El descubrimiento de README no distingue mayúsculas y minúsculas en el nombre base, así que `missions/readme.md` está dentro del alcance junto a las demás raíces de documentación.
2. Todo artefacto de par que exista es completo y coherente: los tres archivos presentes, el blob hash actual de cada lado igual al registrado (editar cualquiera de los lados sin volver a confirmar el par se pone en rojo), el lado chino y cada fuente inglesa de autoría propia con sus selectores de idioma (las fuentes inglesas generadas en la lista están exentas), todo enlace de documento relativo ordinario usa el locale de destino de su lado de origen, y las firmas estructurales coinciden en orden — profundidades de encabezado, bloques de código verbatim (cadena de información y contenido), recuentos de filas y columnas de tablas, tipos de lista, inicios de listas ordenadas, recuentos de elementos y destinos semánticos de enlaces con sufijos de consulta/fragmento exactos, aparte del selector.
3. Los archivos listados como `excluded` no tienen ningún `.zh.md` ni `.i18n.yaml`. Las Agent Notes congeladas bajo `.agents/notes/archived/` quedan fuera de esta compuerta en evolución; su verificador dedicado exige y sella el triplete existente completo en su lugar.

Las compuertas de código orientadas a la fuente consumen una secuencia exacta de vallas `.zh.md` como derivada de su hermano sin sufijo, en lugar de compilar o manifestar el mismo código dos veces. La secuencia debe coincidir en longitud, orden, tipo de valla y cuerpo byte a byte exacto; de lo contrario, ambas copias siguen verificándose de forma independiente y la compuerta de emparejamiento informa del desajuste estructural.

`pnpm run verify-translation-pairing --list` imprime el estado de emparejamiento actual de cada documento dentro del alcance — missing, out-of-sync u ok. Nunca falla; las filas `missing` y `out-of-sync` identifican las violaciones que rechaza la verificación normal.

`pnpm run verify-translation-pairing <pair...>` verifica solo los pares nombrados — cualquiera de los tres archivos de un par (o su nombre base) lo nombra — de modo que un bucle de actualización verifica su propio par en segundos en lugar de volver a escanear el corpus. La forma sin argumentos para todo el corpus es la que ejecutan `doc-sync` y la CI; un verde acotado nunca la sustituye a nivel de PR.

La regla práctica que crea esta compuerta: **cuando un PR edita cualquiera de los lados de un documento emparejado, el mismo PR actualiza la contraparte directamente en una pasada guiada por la terminología y vuelve a registrar el par con `--write <pair>`**, exactamente igual que la regla doc-sync existente del repositorio para el código y los README. Un PR que deja un par desincronizado se pone en rojo en la CI.

El límite de la compuerta, dicho sin rodeos: **una compuerta en verde significa que el par se confirmó coherente con esos contenidos exactos, no que la confirmación fuera sólida.** Verifica hashes y estructura Markdown; no puede juzgar si los dos lados dicen realmente lo mismo, ni si la redacción es precisa, bien terminada y natural — esa es la mitad del contrato que corresponde a la revisión, según [translation-rules.md](translation-rules.es.md). Un par vuelto a registrar con una contraparte chapucera pasa la compuerta; no debe pasar la revisión.

## Alcance y exclusiones

**Alcance**: los documentos raíz CONTRIBUTING y BRAND_GUIDELINES, todos los README ajenos a vendor y todos los documentos activos bajo `.agents/notes/**`, `docs/**` y `python/**`. La coincidencia de README no distingue mayúsculas y minúsculas en el nombre base y cubre directorios futuros sin otra edición del manifest. Los árboles de dependencias y de salidas de build ignoradas y el árbol congelado `.agents/notes/archived/` son exclusiones de descubrimiento, no fuente de traducción en evolución.

Las referencias y gráficos ingleses generados participan en el emparejamiento cuando existe una contraparte china revisada. Sus generadores siguen siendo la fuente de verdad en inglés, y las compuertas de frescura y de emparejamiento imponen sus invariantes respectivos de forma independiente; una regeneración que cambie el inglés deja el par desincronizado hasta que la contraparte china revisada se actualice y se vuelva a registrar. Un generador que posee ambos lados, como el generador de regiones de subsistemas de Cordis, proyecta las rutas de los documentos emparejados a cada locale de salida manteniendo iguales todos los demás bytes generados. Las fuentes inglesas generadas omiten el selector de idioma que llevan las fuentes ordinarias de autoría propia, porque añadirlo dejaría obsoleto al generador; sus contrapartes chinas siguen enlazando de vuelta a la fuente inglesa. La contraparte china de una página generada solo puede reescribir las afirmaciones autorreferenciales de generación y mantenimiento que de otro modo serían falsas para la traducción revisada; todo el contenido técnico sigue sujeto a las reglas ordinarias de fidelidad.

**Excluidos** (nunca se emparejan, y la compuerta rechaza un `.zh.md` o `.i18n.yaml` para ellos):

- [cordis-api/inherited.md](../cordis-api/inherited.md) — generado sin una contraparte china revisada, así que ambos locales del sitio web proyectan la fuente inglesa.
- `docs/AGENTS.md`, `.agents/notes/**/AGENTS.md` y sus enlaces simbólicos de instrucciones `CLAUDE.md` — instrucciones de agent, mantenidas solo en inglés como la raíz `AGENTS.md`.
- `docs/i18n/terminology.md` y [style-samples.md](style-samples.md) — ambos son bilingües por construcción.
- [translation-prompt.md](translation-prompt.md) — la plantilla de prompt del pipeline automatizado; su cuerpo lo consume la máquina verbatim, así que una traducción emparejada cambiaría el comportamiento del pipeline.
- `.agents/notes/archived/` — tripletes históricos congelados. [`verify-archived-agent-notes`](../../scripts/verify-archived-agent-notes.ts) valida su completitud y sus sellos de contenido; el mantenimiento de traducción nunca debe reescribirlos.

**Requisito universal**: todo documento actual o futuro dentro del alcance debe fusionarse como un par bilingüe completo. [scripts/translation-pairing.manifest.json](../../scripts/translation-pairing.manifest.json) contiene solo exclusiones explícitas; no hay lista de despliegue por archivo, fecha límite ni clase de política específica de README.

## División del trabajo

Las contrapartes rutinarias las actualiza directamente el agente que trabaja, de un solo tiro y en una sola pasada, después de cargar [terminology.md](terminology.es.md); no invoca una skill de traducción, no genera un brief, no ejecuta una pasada separada de revisión de traducción ni delega en un subagente. El flujo de trabajo ampliado [dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) conserva esos mecanismos más pesados para la invocación explícita del usuario. La compuerta verifica la completitud del par, los hashes registrados, el enlace de retorno chino y el selector de las fuentes de autoría propia (con la excepción documentada de las fuentes generadas), y su firma estructural documentada. La revisión sigue siendo dueña de la calidad de la traducción, la terminología y los requisitos estructurales que la firma no codifica. El contrato de prompt es ejecutable: [scripts/translation-prompt.ts](../../scripts/translation-prompt.ts) renderiza la plantilla confirmada (terminología inyectada; la plantilla lleva sus propias reglas calibradas) en cualquiera de las dos direcciones y analiza la respuesta de tres secciones, mientras que `verify-translation-prompt` ejercita ambas direcciones de renderizado y el ejemplo incluido en `doc-sync`.
