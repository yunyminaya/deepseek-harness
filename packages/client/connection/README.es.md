# @deepseek-ai/dsh-client-connection

[English](README.md) | Español

Capa consumidora del cable: el apply del plugin de cliente monta `ctx.connection` (cliente de API compartido + estado de loopback de la página actual + `hostDescription` observable con ámbito de generación + arrancador del bucle de streams de un solo consumidor); la cara de export lleva los tipos del contrato de cable, la abstracción `AbstractApiClient` y los tipos de sink/config del bucle. Cada handshake de preparación exitoso publica el valor exacto de `host.describe` antes de `onConnected`; la pérdida de generación y la parada explícita lo limpian, así que los consumidores de capacidad nativa nunca retienen una respuesta desconectada. El carrier de navegador usa HTTP POST para las operaciones unarias y respond y abre un WebSocket solo de bajada por cada uno de `events.mux` y `events.host`; el carrier en proceso satisface la misma abstracción de dos streams. El `ClientTransportHooks` exportado nombra el global de página `__DSH_TRANSPORT__` que reemplaza el carrier de navegador por completo: la app web servida lo deja sin fijar y obtiene HTTP + WebSocket, mientras que un shell que posee un transporte físico distinto (el túnel postMessage de la vista previa del worker) proporciona `createApiClient` y `fetch` — además de `loadBundle` cuando también posee los bytes del bundle — en lugar de bifurcar el plugin. La mitad de Host es dueña de la única ruta `/api` y de su puente Fetch; un interceptor Typert registrado reclama sus endpoints Remote antes del fallback del API Proxy. La clasificación de hostname de loopback permanece interna al paquete: la valla `/api` del Host y las actualizaciones de WebSocket la usan directamente, mientras que otros plugins de cliente consumen el estado derivado `ctx.connection.isLoopback`. La ruta `/api` de la mitad de nodo fija el conjunto de métodos privilegiados (`host.pickDirectory`, `host.openPath` y todo el plano de configuración — `settings.describe`/`openDocument`/`update`/`replace`/`mutate` y `credentials.describe`/`set`/`unset`; lecturas y acciones nativas incluidas, ya que describir devuelve la configuración expuesta, abrir actúa sobre el escritorio del Host y sondear una referencia arbitraria informa de dónde viene una credencial — y el plano de autoría de agent presets, `agentPreset.read`/`copy`/`openDocument`/`remove`, ya que una composición nombra los plugins que ejecuta una sesión, así que leer uno es reconocimiento, y copy/remove/openDocument gestionan la lista y conducen el escritorio del host (la autoría es solo copia, así que ninguno acepta texto de composición ni una ruta); `agentPreset.list` y `agentPreset.select` quedan fuera — la lista lleva solo ids y confianza, y elegir un preset no concede nada que el `agentPreset` propio de `session.create` no concediera, sobre un predeterminado que ya lleva bash) al loopback pasando la valla de confianza con una lista de confianza vacía — una autoridad `trustedHosts` declarada alcanza todos los demás métodos, mientras que estos permanecen locales al loopback hasta que exista una capa de autenticación real. Los carriers de plataforma y el bucle de ConnectionController son internos al paquete; apply los selecciona y los conduce. El límite de bajada está documentado en la [Agent Note del carrier de bajadas WebSocket](../../../.agents/notes/implemented/architecture/2026-08-04-websocket-downlink-carrier.es.md).

## Valla de confianza del navegador /api

La mitad de nodo protege cada entrada bajo `/api` antes de hacer de puente o actualizar (`src/api-request-trust.ts`). Cada petición —marcada por el navegador o no— debe presentar un `Host` que sea una autoridad de loopback o que coincida con una entrada de `trustedHosts`: exacta en las entradas `host:port`, cualquier puerto en las entradas sin puerto, ambos lados comparados mediante normalización WHATWG (defensa contra DNS rebinding). Deliberadamente no hay atajo para las peticiones HTTP sin marcar: sobre HTTP plano un navegador no adjunta ni `Origin` ni Fetch-Metadata a las lecturas de imagen y navegación, así que una petición sin marcar puede seguir siendo una lectura de navegador reboteada con respuesta legible, y Host es la única cabecera que el rebinding no puede falsificar; un handshake de WebSocket de navegador lleva `Origin` y pasa la misma comparación. Los clientes que no son navegador pasan la misma valla mediante loopback, literales de IP LAN derivados del despliegue o una autoridad declarada. Cuando hay marcadores presentes, un `Origin` adjunto debe ser igual a la autoridad del Host, y un marcador explícito `sec-fetch-site: cross-site` se rechaza. Una entrada de `trustedHosts` que no es una autoridad `host[:port]` desnuda y canónica —una que el parsing WHATWG lee exactamente tal como se escribió— hace fallar la carga del plugin ruidosamente: el parsing autorizaría en silencio el hostname dentro de `harness.internal/path`, o ampliaría un puerto de dos puntos colgante o rellenado con ceros a una concesión de cualquier puerto. Los fallos HTTP responden 403 plano antes de cualquier despacho RPC; los fallos de actualización rechazan el handshake antes de que arranque cualquier stream de eventos. Las composiciones que no son de loopback deben confiar explícitamente en sus autoridades servidoras: el runtime Web deriva los literales de IP LAN de una config de servidor de todas las interfaces, mientras que `trustedHosts` en cordis.yml y la bandera `--trusted-host` de la CLI declaran autoridades nombradas. `dsh web --host 0.0.0.0` no se soporta intencionadamente hasta que el acceso remoto tenga una capa de autenticación. La valla es una política de alcanzabilidad, no autenticación; el carrier Web no proporciona ninguna capa de autenticación. Registro de decisión: [la Agent Note del límite de confianza del navegador API](../../../.agents/notes/implemented/architecture/2026-07-28-api-browser-trust-boundary.es.md).

## Bajadas WebSocket `/api`

`/api/events.mux` y `/api/events.host` aceptan cada una una actualización de WebSocket y envían al navegador solo los mensajes de texto `ServerRequest` correspondientes; el cliente no envía datos de aplicación sobre estos sockets. Si cualquiera de los sockets termina, la generación de conexión actual falla y reconstruye ambos streams; la preparación sigue requiriendo que ambos sockets estén abiertos y que la llamada HTTP `host.describe` tenga éxito. El desmontaje del Host termina ambos sockets, aborta sus fuentes y espera la limpieza de las fuentes antes de volver. Los GET de red ordinarios a estas rutas responden 426 sin fallback SSE; el códec SSE de `toFetchHandler` sirve solo al carrier isomórfico en proceso.

## Model Experience

Ninguna, ya que la capa consumidora del cable mueve mensajes ya compuestos entre el navegador y el host; nada de esto llega a una petición de modelo.

Ninguno; este paquete ni ensambla ni envía una petición de provider.

## Limitaciones conocidas y trabajo diferido

- **El historial reanuda una sesión no adjunta** — abrir el historial puede crear el agent del lado del host y añadir latencia a la primera apertura; no hay una ruta de lectura solo de persistencia.
- **El puente `/api` almacena en memoria el cuerpo de cada petición** — `maxRequestBodyBytes` (por defecto 300 MiB, dimensionado para el límite agregado por defecto de 200 MiB de imágenes tras la expansión base64 más el margen de sobrecarga del sobre) es por tanto también el límite residente por petición; se necesitaría una ruta de cuerpo en streaming para bajarlo sin reducir los límites de imagen.
