# `@deepseek-ai/dsh-app-boot`
[English](README.md) | Español

Pegamento de arranque compartido para los app bins ([`dsh`](../../../apps/cli/README.es.md) y [`dsh-acp-demo`](../../examples/acp-demo/README.es.md)): cada bin es una composición fina auto-ejecutable sobre estos helpers, parametrizada por su prefijo de diagnóstico, de modo que el comportamiento ante fallos del loader tiene un único dueño en lugar de divergir entre artefactos publicados.

| Exportación | Rol |
|---|---|
| `resolveConfigPath(path, snapshotMode, cwd?)` | Ruta de configuración absoluta; `snapshotMode === 'replay'` intercambia un nombre base `cordis.yml`/`.yaml` por su hermano `cordis.snapshot.yml` |
| `loadEnv(binName, dir?, warn?)` | Carga el `.env` ignorado por git (Node `process.loadEnvFile`); la ausencia del archivo está bien, uno no cargable advierte con una única línea etiquetada (por defecto: stderr) |
| `loadLayeredEnv(binName, cwd?, warn?)` | Construye la instantánea congelada del CLI de producto heredada > `.env` de proyecto > `.env` de usuario, rechaza las variables de archivo solo de bootstrap y materializa los valores de archivo aceptados sin reemplazar los heredados |
| `installFailLoud(binName, proc?, release?)` | Convierte un rechazo no manejado del arranque o del Loader posterior en una única línea de stderr etiquetada + `exit(1)`; el teardown opcional `release` se espera entre ambos (acotado por `FAIL_LOUD_RELEASE_TIMEOUT_MS`) para que una superficie dueña de la terminal restaure la terminal antes de salir; devuelve el desinstalador |
| `FAIL_LOUD_RELEASE_TIMEOUT_MS` | Cuánto espera `installFailLoud` a su hook `release`; un disposer atascado retrasa la salida fatal, nunca la cancela |
| `assertEntriesLoaded(ctx, binName)` | Lanza una excepción cuando un árbol asentado contiene una entrada habilitada sin fiber, informando de cada nombre de plugin sin resolver como un fallo de arranque de Cordis |
| `assertEntriesActivated(ctx, binName)` | Incluye la comprobación de `assertEntriesLoaded` y luego espera a cada entrada habilitada después de que el Loader se asiente; lanza con el stack original de cada plugin fallido o los servicios sin resolver de cada plugin pendiente |
| `loadOptionalPatches(binName, file)` | Analiza un archivo opcional de lista de patches (el `cordis.patch.yml` de un profile) — un array YAML de nivel superior de `PatchOptions` de include (sobrescrituras de configuración dirigidas por id, listas `insert`, `!!js` permitido); archivo ausente → `undefined`, un archivo ilegible/inanalizable/no-array lanza |
| `loadOverlayPatches(binName, file)` | Analiza un array YAML de nivel superior obligatorio con las mismas entradas `PatchOptions` de include descritas arriba; un archivo ausente también lanza porque el llamador lo nombró |
| `mountRootInclude(ctx, absoluteConfigPath, patches?, bareModuleBaseUrl?)` | Registra los builtins importados estáticamente `cordis:include` y `cordis:group`, monta el include y conserva la entrada raíz exacta que usa el HMR de la capa de patches de usuario; una base de módulo opcional ancla los nombres de paquete desnudos al host instalado mientras que los nombres relativos siguen siendo relativos a la configuración |
| `watchUserPatches(ctx, options)` | Registra el archivo de patches nombrado con el servicio HMR existente de Cordis; cada alta/cambio/eliminación recompones transaccionalmente la lista completa de patches mediante el closure `compose` del llamador (capas propiedad de la app alrededor de la capa de usuario actual) y devuelve un disposer asíncrono |
| `resolveProfileDir` / `initProfile` / `loadProfile` / `readProfileManifest` / `writeProfileManifest` / `resolveBundleDir` / `composeEntries` / `healProfilesModuleFallback` / `PROFILE_TEMPLATES` / `DEFAULT_PROFILE_BUNDLES` / `PROFILES_DIR` / `PROFILE_PATCH_FILENAME` | Maquinaria de profiles (ver [Profiles](#profiles)) |
| `boot(binName, absoluteConfigPath, patches?, prepare?, bareModuleBaseUrl?)` | Crea el contexto raíz, expone `dshHomePath(...segments)` a las expresiones `!!js` de configuración del Loader, instala el Loader, ejecuta la preparación opcional del host antes de que monten las entradas del árbol de configuración (`prepare` puede usar el Loader y aportar slots de contexto propiedad del lanzador), luego monta y espera el árbol de include, afirma que las entradas están cargadas y activadas, y devuelve el contexto raíz — o hace dispose del contexto parcial y rechaza con un error etiquetado; la base de módulo opcional tiene la misma semántica de resolución que `mountRootInclude` |
| `renderConfigDump(binName, absoluteConfigPath, layers, warn?)` | Compone la configuración base y las capas de overlay etiquetadas sin conexión con el analizador y el algoritmo de patches propios del include (`entryListSchema`/`applyEntryPatches`), de modo que el resultado equivale a lo que monta `boot()`, y renderiza YAML con las expresiones `!!js` tal cual; cada tanda de filas que comparte un mismo archivo fuente y las mismas capas de patches va precedida de un comentario `# ==` que nombra ese archivo y esas capas, manteniendo la salida como un único documento cargable; un patch que no coincide con ninguna fila va a `warn` con la etiqueta de su capa (por defecto: una línea de stderr), y los fallos de lectura, análisis o validación de campos lanzan |
| `addHarnessSourceSection(ctx, sourceRoot)` | Añade una sección de prompt global `harness:source` (ordenada justo después de la identidad del harness, antes de la persona) que le dice al agent la ruta en disco del checkout de la implementación de DSH y le advierte que no infiera el directorio de trabajo actual de esa ruta y que use `pwd` en su lugar; es un no-op que devuelve `undefined` cuando el árbol arrancado no tiene ningún servicio `systemPrompt`. La sección se registra contra el fiber de ese servicio, de modo que una recarga HMR de desarrollo del system prompt la elimina hasta el siguiente arranque |
| `HARNESS_SOURCE_SECTION` | El nombre de sección `'harness:source'` bajo el que se registra `addHarnessSourceSection` |

El asentamiento del Loader rechaza los fallos de import y de ciclo de vida con la entrada y la fase que fallan; `boot()` hace dispose del contexto parcial y envuelve ese fallo con el nombre del bin. Las entradas que el asentamiento deja atrás se auditan por separado: `assertEntriesLoaded` convierte una entrada habilitada sin fiber en un rechazo que nombra cada plugin sin resolver, y `assertEntriesActivated` espera a cada fiber fallido para incluir su stack original en el rechazo de arranque y nombra los servicios sin resolver de cada entrada pendiente. Antes de lanzar, la auditoría marca esas razones de rechazo exactas mediante un único checkpoint de proceso, de modo que `installFailLoud` fusiona la notificación duplicada del Loader mientras todo rechazo no manejado no relacionado sigue siendo fatal.

El Loader monta las entradas de forma concurrente, así que una superficie ya puede ser dueña de la terminal cuando falla otra cosa: salir sin el teardown propio del árbol dejaría el modo raw, el bracketed paste y el protocolo de teclado activados en la shell del usuario, y la respuesta de una consulta de terminal en vuelo aterrizaría como texto literal en el siguiente prompt. Un fallo del árbol de configuración se asienta a través de `boot()`, cuyo dispose del contexto parcial ejecuta el apagado propio de la superficie antes del rechazo etiquetado. Para los rechazos que `boot()` no puede ver — trabajo asíncrono desacoplado de un plugin que se rechaza durante o después del montaje — un bin dueño de la terminal pasa `release` para hacer dispose del árbol antes de que la salida se confirme; `dsh` captura el contexto raíz en el hook `prepare` de `boot()` en lugar de hacerlo desde su valor de retorno, de modo que el hook cubre toda la ventana de montaje. Mientras un release está en vuelo, el handler permanece instalado y enganchado: el primer rechazo es el que se informa, y los rechazos posteriores (incluido el del propio teardown) se tragan en lugar de quedar sin capturar y matar el proceso a mitad del teardown.

`cordis:group` se registra junto a `cordis:include` para que una composición pueda dar un mismo ámbito `isolate` a un provider y a sus consumers juntos. Ambos se cargan a través de la canalización de módulos ambiente en lugar de la resolución de especificadores propia del árbol incluido, que es lo que permite que una composición fuera de este workspace — un preset de agent bajo el home de Harness — use una fila de group.

Los especificadores de plugin desnudos de una configuración (`@deepseek-ai/dsh-*`, paquetes npm) se resuelven mediante el loader de módulos interno del Loader de Cordis. Se resuelven desde el directorio de configuración por defecto; un runtime cerrado pasa `bareModuleBaseUrl` a `boot` o `mountRootInclude` para que su árbol de paquetes instalado siga siendo autoritativo aunque la configuración viva dentro de otro proyecto Node. Los especificadores relativos siempre se resuelven contra el directorio de configuración. Los bins del repositorio instalan el peer opcional `node-addon-require-builtin` del Loader; los llamadores externos deben suministrarlo o instalar los plugins donde la resolución de imports de Node plano pueda encontrarlos. El artefacto compilado `dsh-app-boot` incorpora la implementación de Include montada estáticamente mientras deja al Loader externo, de modo que el árbol de include y el host se vinculan a un único peer de Loader. La ruta de fuente `pnpm dsh` además mapea los paquetes de workspace declarados en el manifest a su fuente TypeScript; su verificación de configuración exige que todo plugin desnudo raw/Web distribuido aparezca en los `dependencies` del manifest del resolver.

Este paquete no lleva hooks de loader ni superficie de modo de desarrollo. La [`dsh` app](../../../apps/cli/README.es.md) es dueña de su hook de lanzamiento de fuente Node y consume estos helpers para la secuencia de arranque; los consumidores compilados siguen usando la resolución de paquetes Node plana.

## Profiles

Un profile es un directorio bajo `$DSH_HOME/profiles/<name>` (el home de Harness se resuelve mediante [`resolveDshHome`](../../util/home-paths/README.es.md): `$DSH_HOME`, si no `~/.dsh`) que contiene un `package.json` — `dependencies` de plugins fuera del árbol más el manifest de profile `dsh.profile` con su lista ordenada de capas `bundles` — y el `cordis.patch.yml` propio del usuario. Un bundle es un paquete npm cuyo manifest declara `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`; `loadProfile` resuelve cada nombre de `dsh.profile.bundles` con doble anclaje (primero la instalación de dsh, luego el directorio del profile) y falla en voz alta ante un paquete listado sin declaración de bundle. `composeEntries` aplica capas de patches sobre una lista de entradas vacía mediante el `applyEntryPatches` propio del include, de modo que la composición, la derivación de flags y los dumps de configuración no pueden divergir de lo que arranca. `healProfilesModuleFallback` mantiene el directorio plano `$DSH_HOME/profiles/node_modules` — un symlink por cada paquete del que dependen la app de la instalación y sus bundles — de modo que los nombres de plugin desnudos de cualquier profile se resuelven mediante el recorrido parental ordinario de Node sin que pnpm gestione los paquetes dentro de la caja. `PROFILE_TEMPLATES` (`web`, `headless`) se auto-inicializan en el primer uso; otros nombres fallan en voz alta hasta que `initProfile` los crea (la ruta `dsh plugin`). `loadProfile` normaliza una tupla de bundle exacta propiedad de la instalación a su plantilla distribuida mientras preserva todos los demás campos del manifest; cualquier entrada adicional, ausente o reordenada convierte la lista en propiedad del usuario y la deja sin cambios.

Las preferencias de nivel de usuario locales a la máquina también viven en el home de Harness:

- **`.env`** — las capas de entorno ordinarias del CLI de producto: el archivo del directorio invocador supera al archivo del home de Harness, y ambos quedan por debajo del entorno heredado. `loadLayeredEnv` hace una instantánea del origen de cada valor, rechaza las [variables de archivo solo de bootstrap](../../../.agents/notes/implemented/architecture/2026-08-04-configuration-source-ownership.es.md#decision) sin distinguir mayúsculas y materializa los valores aceptados en `process.env` para las expresiones del Loader y las bibliotecas de terceros. Las credenciales gestionadas viven por separado en [`.credentials.yaml`](../../credentials/credentials-local/README.es.md); una credencial dejada en cualquiera de los `.env` sigue siendo un respaldo de menor prioridad.
- **`cordis.patch.yml`** (nivel de home) y **`profiles/<name>/cordis.patch.yml`** — las capas de patches del usuario, aplicadas después de cada capa de bundle (primero el archivo por-profile, luego el de nivel de home, que por tanto lo supera): un patch dirigido por id reemplaza todo el `config` de la entrada nombrada (reafirma los campos sin cambios), `insert` añade entradas y las expresiones `!!js` interpolan en el montaje. Un patch que nombre un id de entrada ausente del árbol compuesto es una advertencia de stderr. Un archivo vacío o solo de comentarios lanza (se analiza como nada, no como una lista); desactiva la capa con `[]`.

Cada arranque de profile mantiene `cordis.patch.yml` vivo mediante `watchUserPatches` (una superficie de un solo uso hace dispose del watcher a través de su apagado acotado). El watcher apunta a la ruta exacta aunque el archivo o su padre inmediato no existan, serializa las ráfagas y recompones los patches del usuario dentro del orden de capas del llamador (capas de bundle abajo, overlays arriba). Una lectura, un análisis o un candidato de Loader rechazados dejan en marcha el último árbol bueno y el servicio HMR difunde `hmr/config-update-failed(filename, Error)` después de registrarlo; los fallos de los observadores quedan contenidos. Hacer dispose del contexto cierra el watcher y drena una actualización activa.

## Experiencia de modelo

Indirectamente, mediante el árbol de plugins que carga, que determina los prompts, schemas, mensajes y el adaptador de modelo de la aplicación resultante; la única exportación que aporta texto visible para el modelo, `addHarnessSourceSection`, lo hace solo cuando un consumidor la llama después del arranque.

#### Efecto de KV Cache

Ninguna invalidación directa desde `boot()`; un consumidor que llama a `addHarnessSourceSection` coloca una línea corta cerca del inicio del system prompt, antes del contenido por petición, de modo que no invalida la caché entre turnos, y cualquier otro cambio del prefijo de petición es propiedad del consumidor nombrado.

## Limitaciones conocidas y trabajo diferido

- **Los especificadores de paquete desnudos dependen de los internals del Loader** — los bins de producción necesitan el helper nativo opcional del Loader; un llamador en proceso sin él debe usar especificadores relativos/de archivo resolubles o aportar su propio hook de resolución de módulos.
- **El intercambio de reproducción de instantáneas depende del nombre base** — solo una configuración que termina en `cordis.yml` o `cordis.yaml` se mapea al hermano `cordis.snapshot.yml`; los nombres de configuración personalizados requieren selección gestionada por el llamador.
- **El descubrimiento de entorno está acotado al lanzamiento** — `loadLayeredEnv` lee solo el directorio de invocación y el home de Harness una vez; no busca en los padres ni sigue un workspace seleccionado después. `loadEnv` sigue siendo el helper de un directorio para los bins que no son de producto.
- **Un patch de usuario reemplaza toda la configuración coincidente** — un patch dirigido por id no hace deep-merge, así que una sobrescritura de profile reafirma los campos del bundle que conserva.
