# @deepseek-ai/dsh-llm-pi-ai

[English](README.md) | Español

Adaptador multiprovider genérico para el seam de LLM (modelo de lenguaje de gran tamaño) del harness, respaldado por [`@earendil-works/pi-ai`](https://www.npmjs.com/package/@earendil-works/pi-ai). Una instancia del plugin posee un dict de perfiles de provider con clave por ruta; cada petición selecciona un perfil con `GenerateOptions.provider` y resuelve `GenerateOptions.model` contra el catálogo configurado de esa ruta. Una ruta que nombra un provider de pi-ai instalado hereda su endpoint, su protocolo wire y su catálogo de modelos como valores por defecto y los sobrescribe campo a campo; una ruta que pi-ai no incluye se declara por completo, de modo que un gateway compatible con OpenAI, un servidor autoalojado o un provider más reciente que el catálogo instalado son configuración y no un cambio de código.

La raíz del paquete expone el contrato de plugin de Cordis, `PiAiAdapter` y `supportedProtocols()`; la resolución de perfiles, la materialización del catálogo, la construcción de providers, la conversión de replay y la conversión de streams siguen siendo internas del paquete.

## Configuración

Configura las credenciales, el catálogo de modelos y los ajustes de transporte específicos del despliegue por provider, con la propia ruta del provider como clave. Cada perfil puede fijar un `retryPolicy`; la omisión usa el modo normal con cinco reintentos. `apiKeyEnv` es una *referencia* de credencial que se resuelve en cada petición, de modo que ningún secreto entra en este archivo. Omitirla deja la ruta sin autenticar, lo que para una ruta de catálogo instalado significa el descubrimiento ambiental nativo del provider de pi-ai; una referencia configurada que no resuelve a nada falla la petición con `MISSING_CREDENTIAL`, porque si se dejara caer autenticaría con la clave no relacionada que el entorno tuviera a mano. Una credencial sirve a todos los modelos de su ruta.

```yaml
- id: llm
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      # Catalog route: endpoint, protocol, and models all come from pi-ai.
      openai:
        apiKeyEnv: OPENAI_API_KEY
        baseURL: https://proxy.example.com:8443
        reasoning: high
        requestImagePixelBudget: 4194304 # total pixels; 2048 by 2048 default
        requestImageMaxBytes: 1048576    # raw bytes before base64 expansion
        maxRequestImageBytes: 20971520   # accumulated base64 payload
        retryPolicy:
          mode: normal
          maxRetries: 3
          backoff:
            initialDelayMs: 500
            maxDelayMs: 10000
            jitterRatio: 0.1
      # Catalog route with its catalog narrowed to one model and that model's
      # capacity corrected; every unset field still comes from the catalog.
      anthropic:
        apiKeyEnv: ANTHROPIC_API_KEY
        streamIdleTimeoutMs: 300000
        models:
          - id: claude-sonnet-4-5
            contextWindow: 200000
      # Catalog route with one model reshaped in place; the rest of the
      # catalog keeps serving (a models list would replace it instead).
      deepseek:
        apiKeyEnv: DEEPSEEK_API_KEY
        modelOverrides:
          deepseek-v4-pro:
            reasoningEfforts:
              off:
              high: high
      # Hand-declared route: pi-ai ships nothing under this key, so the profile
      # supplies the whole provider.
      acme-gateway:
        displayName: Acme Gateway
        apiKeyEnv: ACME_GATEWAY_API_KEY
        api: openai-completions
        baseURL: https://gateway.acme.example/v1
        # Request shape for an endpoint whose URL pi-ai cannot recognize; it
        # would otherwise be addressed as though it were OpenAI itself.
        compat:
          thinkingFormat: deepseek
          supportsDeveloperRole: false
          maxTokensField: max_tokens
        models:
          - id: acme-large
            name: Acme Large
            contextWindow: 65536
            maxTokens: 4096
          - id: acme-think
            name: Acme Think
            contextWindow: 262144
            maxTokens: 32768
            # key = selectable level, value = its wire spelling; only off may
            # leave the value empty (supported, send nothing).
            reasoningEfforts:
              off:
              high: high
              max: ultra
```

La forma de dict hace que las rutas duplicadas sean irrepresentables, y la forma de array anterior al release (con campos `provider` por perfil) falla al cargar con indicaciones de migración. `providers` también puede estar vacío u omitirse por completo: el adaptador se monta entonces **dormido** — cero rutas, sin entradas extra de catálogo — y registra rutas en el momento en que la sección de ajustes `llm-pi-ai:` suministra perfiles, dejándolas caer de nuevo cuando se vacía. Dormido o no, el plugin declara cada provider de catálogo instalado en el directorio de providers configurables (`ctx.llm.listConfigurableProviders()`, ruta de ajustes `providers.<provider>`), junto con cada ruta que declaran los perfiles actuales, de modo que las superficies de configuración pueden ofrecer el catálogo completo antes de que exista ruta alguna y aun así pueden dirigirse a una declarada a mano. Cada entrada lleva `declared`: si pi-ai no incluye nada bajo esa clave. Sigue al catálogo instalado, nunca al documento de ajustes, porque estrechar los modelos de un provider incluido también almacena un perfil y esa ruta sigue siendo una que pi-ai conoce — solo el adaptador puede distinguirlas, por eso responde el directorio en lugar de dejar que una superficie lo infiera. Qué adaptadores existen es composición; qué providers se ejecutan puede ser enteramente el documento de ajustes del usuario. El registro con `ctx.llm` es atómico: una colisión con cualquier ruta de provider ya poseída por otro adaptador falla la carga del plugin sin registrar las rutas restantes. Los ids de modelo no son config de ciclo de vida; un modelo que la ruta no configura falla antes de cualquier petición al provider con `LlmError('UNKNOWN_MODEL')`.

## Resolución del catálogo

La lista `models` de un perfil *sustituye* al catálogo instalado de la ruta en lugar de ampliarlo; omitirla (o dejarla vacía) sirve ese catálogo sin cambios. Cada entrada toma por defecto sus campos sin fijar del modelo instalado del mismo `id`, de modo que estrechar una ruta de catálogo a dos modelos, corregir una capacidad o añadir un modelo más reciente que el catálogo instalado son ediciones de una línea — pero declarar cualquier lista `models` significa que todos los modelos que la ruta debe seguir sirviendo deben aparecer en ella, bastando una entrada con solo `id`. Los campos configurables de la entrada son `id`, `name`, `contextWindow`, `maxTokens`, `reasoningEfforts` y `compat`. Los precios y las modalidades de entrada no tienen consumidor en el harness y viajan con la entrada instalada o están ausentes.

`modelOverrides` remodela modelos individuales del catálogo instalado sin ese coste: cada clave es un id de modelo del catálogo, cada valor son los mismos campos que acepta una entrada `models` con el id viviendo en la clave, y el resto del catálogo sigue sirviendo intacto — «corrige un modelo, conserva los otros treinta y siete» como edición de tres líneas. Un override se convierte en la configuración de esa entrada de catálogo, de modo que capacidades, esfuerzos y compat se resuelven por el mismo camino, con los mismos diagnósticos y la misma semántica de valores por defecto de petición que una entrada `models`. Los overrides solo tienen sentido en una ruta de catálogo que sirve su catálogo: uno colocado junto a una lista `models` (que ya sustituye al catálogo), en una ruta declarada a mano (cuyos modelos están escritos por completo en `models`), o que nombra un modelo que el catálogo no describe, se rechaza en lugar de omitirse, porque un modelo silenciosamente sin cambios es una errata que alguien tendría que perseguir.

### Esfuerzos de razonamiento por modelo

`reasoningEfforts` declara los niveles de pensamiento seleccionables de un modelo: cada clave es un nivel que ofrecen los selectores, su valor es la grafía que el despacho envía por el wire, de modo que `high: high` deja pasar el nombre canónico mientras que `max: ultra` lo renombra para un gateway con vocabulario propio. Las claves vienen del conjunto de niveles de pi-ai (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`); un nivel no declarado no se ofrece. Omitir el campo conserva la capacidad de la entrada del catálogo instalado (un modelo declarado a mano no tiene ninguna y no razona); `false` declara un modelo sin razonamiento, que es como un perfil retira el razonamiento de un modelo de catálogo que su gateway no puede servir; una declaración vacía se rechaza en lugar de adivinar entre esos dos significados.

La declaración se traduce a `Model.reasoning` + `thinkingLevelMap` de pi-ai con cada nivel decidido explícitamente — los niveles no declarados quedan fijados como no soportados en lugar de dejarlos al valor por defecto de pi-ai, que es asimétrico (una clave ausente significa «soportado» para los cinco niveles base pero «no soportado» para `xhigh`/`max`) y que un autor de perfiles no debería tener que conocer. `off` es la única clave de tres estados: omitida, los selectores no ofrecen Off y una petición explícita de Off se rechaza — una petición que no nombra esfuerzo alguno sale igualmente sin el parámetro, de modo que lo que haga entonces el provider es su propio valor por defecto; declarada sin valor (`off:`), Off se ofrece y seleccionarlo no envía nada — para el dialecto `deepseek`, un `thinking: {type: "disabled"}` explícito — lo que también cubre una petición que no nombra esfuerzo alguno; declarada con un valor (`off: none`), ese valor viaja por el wire como parámetro de esfuerzo. No existe grafía para devolver una clave del mapa del catálogo a «sin fijar»: la declaración es toda la oferta, así que repite los niveles del catálogo que conserves.

### Conmutadores de compatibilidad wire

pi-ai da forma a cada petición a partir del id del provider y del baseURL: qué rol lleva el prompt del sistema, qué campo limita la salida, cómo viaja un nivel de pensamiento. La URL de un gateway privado no dice nada, y para un endpoint que pi-ai no reconoce la detección responde como si fuera el propio OpenAI — el prompt del sistema de un modelo de razonamiento sale como `developer`, el límite de salida como `max_completion_tokens`, el nivel de pensamiento como un `reasoning_effort` pelado — y la mayoría de los gateways compatibles con OpenAI rechazan al menos uno de ellos. Por eso `compat` es configurable en la ruta (valor por defecto de sus modelos) y por modelo (gana por campo), resolviendo modelo → ruta → entrada del catálogo instalado → detección propia de pi-ai; un conmutador a nivel de ruta ensombrece el valor de la entrada del catálogo para todos los modelos que lo leen, y no existe grafía para devolver un campo al catálogo salvo redeclarar su valor.

Cada conmutador pertenece a los protocolos cuyo tipo de compat de pi-ai lo declara, y el agrupamiento sigue el *tipo* de compat en lugar del nombre del protocolo: los tres protocolos Responses (`openai-responses`, `azure-openai-responses`, `openai-codex-responses`) comparten un tipo de compat, de modo que un conmutador fijable en uno lo es en los tres. `supportsDeveloperRole` se puede fijar en `openai-completions` y en esos tres; `thinkingFormat` solo en `openai-completions`; `supportsTemperature` solo en `anthropic-messages`; `supportsStrictMode` alcanza también a `bedrock-converse-stream`. Un conmutador a nivel de modelo que su protocolo no acepta falla la resolución nombrando lo que ese protocolo sí ofrece; uno a nivel de ruta aterriza en los modelos que lo leen y salta el resto, y se rechaza solo cuando ningún modelo de la ruta podría leerlo.

Tres tipos de clave se rechazan en lugar de descartarse: una que ningún protocolo declara (una errata), una que el catálogo instalado de pi-ai posee para un proveedor concreto (`openRouterRouting`, `zaiToolStream`, `deferredToolsMode`, `sessionAffinityFormat`, `supportsOpenAIGrammarTools`, `supportsToolSearch`, `supportsExplicitPromptCacheMode`, `supportsToolReferences`, `vercelGatewayRouting`, `sendSessionAffinityHeaders`) — una ruta que necesita el conmutador propio de un proveedor es una ruta de catálogo que debería nombrarse como tal — y una escrita sin valor alguno (`supportsDeveloperRole:`), que schemastery deja pasar como null y que de otro modo sustituiría el valor del catálogo instalado por nada. El conjunto ofrecido queda fijado a los cuatro tipos de compat de pi-ai mediante puertas de deriva (drift gates), los protocolos que los llevan se derivan del propio `Model.compat`, y el tipo de cada campo se deriva de upstream en lugar de redeclararse, de modo que una actualización que añade un campo, da a otro protocolo un tipo de compat o amplía una unión de valores falla la build hasta que alguien la clasifica.

Un modelo que ni la entrada ni el catálogo instalado dimensionan toma el `defaultContextWindow` de la ruta (262,144) y su `defaultMaxTokens` (32,768), de modo que un listado que no revela más que ids produce aun así una ruta servible. Ambos fallbacks son conjeturas por construcción, por eso son campos de ruta que un despliegue cuyo gateway sirve modelos más pequeños corrige una vez, en lugar de constantes enterradas en el adaptador; el fallback dimensiona el modelo y nunca se convierte en un tope por petición.

Las modalidades de petición resuelven entrada `input` → entrada del catálogo instalado → `defaultInput` de la ruta (por defecto `[text]`), el mismo orden y el mismo papel de fallback que usan las capacidades anteriores. Así, un modelo de catálogo conserva las modalidades que el catálogo registra para él, y un valor por defecto de ruta más estrecho nunca se las retira; un gateway cuyos modelos *no descritos* aceptan todos imágenes declara `[text, image]` una vez en la ruta en lugar de en cada entrada. La lista vacía de una entrada significa lo mismo que una ausente — describe un modelo que no acepta nada, así que no afirma respuesta alguna y la resolución continúa más allá de ella, que es lo que conserva las modalidades propias de un modelo de catálogo cuando una entrada `models` lo nombra sin declarar ninguna. La de la ruta no puede estar vacía, porque nada queda por debajo para responder en su lugar.

`[text]` es la ausencia de declaración más que una conjetura sobre el endpoint, por eso el fallback aquí es conservador donde los fallbacks de capacidad son meramente plausibles. Nada interroga a un gateway sobre lo que acepta, y las dos respuestas erróneas no cuestan lo mismo: el harness rechaza una imagen antes de adjuntarla cuando las modalidades de un modelo la omiten, de modo que declarar de menos cuesta un rechazo que nombra el modelo, mientras que declarar de más admite una imagen que el provider rechaza después a mitad de turno — cuando el mensaje ya es duradero, lo que deja a la sesión repitiendo una petición que no puede tener éxito.

La resolución sigue fallando en voz alta, nombrando la ruta y el modelo culpables, cuando una ruta no puede servirse en absoluto: una ruta que el catálogo no incluye necesita `api`, `baseURL` y una lista `models` no vacía de modelos identificados de forma única. Esa resolución se ejecuta dentro del schema de la sección, así que un perfil inservible se rechaza **donde se escribe** — `settings.mutate` responde `settings-rejected` nombrando la ruta y el modelo — en lugar de almacenarse y luego deshabilitar en silencio todas las rutas del namespace. El seam de ajustes conserva el último valor bueno de un namespace para una sección ya almacenada que falla, de modo que esto no puede dejar varado un despliegue. `api` acepta los protocolos de `supportedProtocols()` y solo hace falta cuando el catálogo no puede suministrar uno: un modelo ausente del catálogo hereda el protocolo en el que coinciden sus hermanos incluidos, así que añadir un modelo a una ruta de catálogo de un solo protocolo no redeclara nada.

`baseURL` fija el endpoint de todos los modelos de la ruta, de modo que los proxies privados como `https://proxy.example.com:8443` siguen siendo compatibles; una ruta de catálogo que lo omite conserva el endpoint propio de cada modelo del catálogo. Nombrar `api` en una ruta de catálogo reorienta toda la ruta a ese protocolo, que es como un despliegue mueve un provider entre, digamos, Responses y Chat Completions.

`supportedProtocols()` es deliberadamente más estrecho que el conjunto completo de la API de streaming de pi-ai: solo contiene los protocolos que un perfil puede describir *por completo* con una clave, un endpoint y cabeceras. Bedrock firma con SigV4 sobre credenciales de AWS y una región, Vertex necesita un proyecto, una ubicación y credenciales de aplicación por defecto, Azure necesita el entorno del provider más una api-version, y Codex autentica vía OAuth — ofrecerlos devolvería una ruta que no puede autenticar. Las rutas de catálogo siguen alcanzándolos a través de su propio provider; solo se rechaza un override explícito.

## Configuración dinámica (ajustes + credenciales)

El adaptador lee sus perfiles a través de un thunk **una vez por operación** en lugar de congelarlos en la construcción. El plugin registra el namespace `llm-pi-ai` en el seam opcional `ctx.settings` con este mismo schema `Config` y su entrada `cordis.yml` como `base` de la composición, y como `providers` es un dict, la base y la sección de ajustes `llm-pi-ai:` del usuario se fusionan **por provider**: un usuario puede añadir una ruta, sobrescribir un campo de una ruta de composición o apuntar una ruta a otro proxy, todo efectivo en la siguiente petición sin reiniciar. Sin un servicio de ajustes montado, solo la config de la entrada conduce al adaptador, sin cambios.

Las credenciales se resuelven por llamada de stream a través de `apiKeyEnv` y del seam opcional `ctx.credentials`; sin ese seam, el adaptador lee exactamente la variable de entorno referenciada. Un perfil que no nombra credencial alguna — y solo ese caso — difiere al descubrimiento ambiental de pi-ai. Cada clave resuelta se recorta y se comprueba su formato antes de usarla, de modo que un valor que ninguna cabecera HTTP puede llevar se rechaza en lugar de aflorar como un `TypeError` opaco de `fetch`; el rechazo lanza `LlmError('INVALID_CREDENTIAL')` nombrando la ruta y la referencia de credencial que fallan, pero nunca parte alguna de la clave. El conjunto de rutas y la política de reintento capturada de cada ruta son los hechos a nivel de registro: cuando cualquiera de los dos cambia, el plugin sustituye su registro atómicamente (misma instancia del adaptador, conjunto de candidatos validado primero), de modo que una ruta que otro adaptador ya posee deja a las rutas anteriores sirviendo y revertir a una configuración que funciona se vuelve a aplicar. El orden de las claves de provider nunca cuenta como cambio. Una sección que este adaptador no pudiera servir se rechaza donde se escribe — el `validate` registrado resuelve todo el conjunto de perfiles, así que `ctx.settings.mutate` rechaza con el error propio del resolver (la superficie wire lo informa como `settings-rejected`) y no se almacena nada. Una sección almacenada que se vuelve inservible de otra manera — una edición externa de `settings.yaml` — conserva el último valor bueno del namespace en el seam de ajustes y avisa. La propia config de la entrada sigue fallando la carga del plugin, y una ruta que el registro de llm rechaza (una que otra familia de adaptadores ya posee) se registra en el log mientras las rutas registradas antes siguen sirviendo.

El adaptador expone los modelos de cada ruta configurada a través de `ctx.llm.listModels(provider)`. Esto es metadatos de selector neutrales respecto al provider leídos de la misma colección `Models` de pi-ai que usa la ruta de petición, de modo que el descubrimiento no crea un segundo registro de modelos. `ctx.llm.resolveModelInfo(provider, model)` realiza esa búsqueda exacta de descriptor una vez y devuelve su identidad, su ventana de contexto, su tope de salida configurado y sus niveles de pensamiento seleccionables, manteniendo los metadatos autoritativos en el adaptador dueño de la ruta y no en sus consumidores. El `maxTokens` **configurado** de un modelo se convierte en el `defaultMaxTokens` del seam, de modo que una petición que no nombra tope de salida lleva el que eligió el despliegue; un valor heredado del catálogo instalado es la *capacidad* de salida del modelo y nunca se convierte por sí solo en un valor por defecto de petición.

Un modelo que lleva metadatos de razonamiento — del catálogo instalado o de su `reasoningEfforts` de entrada — expone el resultado ordenado de `getSupportedThinkingLevels(model)` de pi-ai sin filtrado ni normalización, incluidos `off` y la disponibilidad específica del modelo de `xhigh` o `max`. El Harness expone cada nivel canónico de pi-ai como un ID opaco; las grafías wire de provider/modelo permanecen dentro del `thinkingLevelMap` de pi-ai.

Un modelo **sin** esos metadatos — uno declarado a mano cuya entrada no declara `reasoningEfforts`, y un modelo de catálogo que pi-ai marca como no razonador — no expone `reasoning` en absoluto. pi-ai informa de un modelo así como soportando el único nivel `off`, pero `off` se traduce a *omitir* la opción de razonamiento, que es byte a byte la petición que ya produce no nombrar esfuerzo alguno: seleccionarlo no podría deshabilitar nada, así que un provider cuyo valor por defecto propio es pensar seguiría pensando con `off` mostrado como seleccionado. Informar de la capacidad como no disponible deja una superficie que ofrece el valor por defecto del provider y nada que lo tergiverse. El valor `reasoning` del perfil, incluido `off`, es el valor por defecto del despliegue cuando está configurado; omitirlo conserva el valor por defecto del provider. El `GenerateOptions.reasoningEffort` por petición tiene precedencia, y un nivel ausente de la capacidad exacta del modelo falla la PETICIÓN con `UNSUPPORTED_REASONING_EFFORT` antes de la I/O de red en lugar de recortarse. Describir un modelo nunca falla así: los modelos de un mismo provider no coinciden en qué niveles aceptan, así que `resolveModel` informa de un nivel de perfil que el modelo exacto no puede tomar como ningún valor por defecto en lugar de lanzar. Un throw allí sacaría a todo el provider de cada catálogo de modelos construido sobre él — un campo de perfil mal fijado ocultando incluso los modelos que sí soportan el nivel — así que una configuración mala aflora donde se actúa sobre ella, no donde se describe. Las opciones comunes de stream de pi-ai representan `off` omitiendo `reasoning`.

Los campos de perfil soportados son `apiKeyEnv`, `displayName`, `api`, `baseURL`, `models`, `modelOverrides`, `compat`, `defaultContextWindow`, `defaultMaxTokens`, `defaultInput`, `headers`, `reasoning`, `thinkingBudgets`, `cacheRetention`, `transport`, `timeoutMs`, `websocketConnectTimeoutMs`, `streamIdleTimeoutMs`, `maxRequestImageBytes`, `requestImagePixelBudget`, `requestImageMaxBytes` y `retryPolicy`. Cada política de reintento de perfil resuelta se captura con su ruta de provider; la omisión usa el valor por defecto normal acotado compartido de cinco reintentos. El intervalo de stream ocioso es un retraso de timer de Node positivo y finito, tiene por defecto cinco minutos y cubre solo una lectura pendiente del provider, no el tiempo de pensamiento del consumidor. Cada ruta de imágenes deriva una versión de petición determinista del adjunto normalizado independiente del provider bajo `requestImagePixelBudget` (por defecto 2048 por 2048 píxeles totales) y `requestImageMaxBytes` (por defecto 1MiB de bytes en bruto). Antes de leer los adjuntos, `maxRequestImageBytes` se aplica a los límites superiores conservadores de la versión de petición y sustituye las imágenes más antiguas que exceden el presupuesto por texto fijo; las longitudes exactas de base64 se vuelven a comprobar después de generar las versiones retenidas. El valor por defecto de 20MiB puede retener quince versiones de 1MiB de tamaño máximo tras la expansión base64 dejando a la vez margen en el cuerpo de la petición. La misma versión alimenta el base64 en línea, y su descriptor estable expone el id del adjunto y las dimensiones reales de la imagen de petición. La atribución de app del harness gana frente a un nombre de cabecera configurado en conflicto.

El adaptador fuerza a cero el `maxRetries` del SDK de pi-ai para que una llamada a `stream()` haga una petición al provider. Los campos de perfil eliminados `maxRetries` y `maxRetryDelayMs` fallan al cargar en lugar de multiplicar u ocultar en silencio el presupuesto de reintentos a nivel de agent (agente) compuesto por separado. La expiración por inactividad aborta la señal de petición estable del SDK y aflora `TIMEOUT`; un abort anterior del llamante permanece como `ABORTED`.

## Interrogación de endpoints

El plugin ofrece `ctx.llm.registerModelDiscovery('llm-pi-ai', …)`, que responde «¿qué modelos puede servir este provider?» para una ruta que una superficie de configuración está editando o redactando. Deliberadamente *no* es una actualización del catálogo: no se almacena nada, y la respuesta son candidatos que la superficie ofrece para adoptar. `settings.yaml` sigue siendo lo único que decide qué sirve una ruta.

Una petición que nombra una ruta que el **catálogo instalado incluye se responde desde ese catálogo**, sin llamada de red: el registro de pi-ai es la lista autoritativa de sus propios providers, y lleva las ventanas de contexto y los topes de salida que un endpoint de listado no revelaría. Una ruta así no necesita `baseURL` en absoluto. Solo una ruta que el catálogo no describe — un gateway, un servidor autoalojado — se interroga por el wire, y a una que no nombra endpoint se le dice que fije uno o que introduzca sus modelos a mano.

Un borrador lleva la credencial que el usuario escribió, si la hay; una ruta que ya almacenó una muestra a una superficie de configuración solo un descriptor redactado, así que la interrogación resuelve el `apiKeyEnv` de esa ruta en lugar de salir sin autenticar e informar del 401 del endpoint como una clave equivocada. Una clave escrita gana, por ser la que está bajo prueba. La resolución ocurre solo en el camino que llega a la red, de modo que una ruta de catálogo responde sin tocar credenciales en absoluto. Una clave de prueba suministrada o almacenada se recorta y se comprueba su formato del mismo modo, así que un valor que ninguna cabecera HTTP puede llevar se rechaza de inmediato como `LlmError('INVALID_CREDENTIAL')` en lugar de llegar a `fetch`, donde afloraría como un fallo opaco de `ByteString` indistinguible de un endpoint inalcanzable.

La interrogación lee `openai-completions` y `openai-responses`, cuya forma de `GET /models` con auth de bearer es la única en la que coinciden un gateway, un servidor autoalojado y los endpoints oficiales. Azure queda excluida pese a su linaje OpenAI — autentica con una cabecera `api-key` y exige una query `api-version` — y Codex usa OAuth; cualquier otro protocolo responde `DISCOVERY_UNSUPPORTED` para que la superficie vuelva a la entrada a mano en lugar de informar de un fallo de autenticación como un provider sin modelos. El `baseURL` se trata como un prefijo y no como una URL contra la que resolver, de modo que una ruta de despliegue como `https://gateway.example/openai/v1` conserva sus segmentos.

La mayoría de los listados revelan un id y nada más; `context_window`/`context_length` y `max_output_tokens`/`max_tokens` se leen cuando un gateway los suministra, las entradas sin un id utilizable se omiten en lugar de hacer fallar todo el listado, y todo lo demás sigue debiéndolo la superficie que adopta. La respuesta se lee bajo un techo de cuatro megabytes aplicado a los bytes realmente recibidos — el endpoint es una URL que el usuario escribió, así que una longitud declarada se comprueba primero pero nunca se confía en ella como límite. Un endpoint inalcanzable, una credencial rechazada, un cuerpo no JSON y un cuerpo sin array `data` fallan todos con `DISCOVERY_FAILED` y un mensaje que nombra el endpoint y, solo para un 401 o 403, la credencial. La cancelación durante la lectura del cuerpo aflora como `ABORTED`, como una cancelación antes de que la petición saliera.

## Enrutamiento de provider/modelo y replay

Cada resolución produce una instantánea **inmutable** — los perfiles más una colección `createModels()` que contiene el `Provider` que construyó cada ruta — y toda operación captura una instantánea completa antes de su primer `await`. Un cambio de configuración construye una colección *nueva* en lugar de mutar la que está en uso: `Models.streamSimple()` resuelve su provider perezosamente, cuando el stream se consume por primera vez, que es después del await de credencial, así que una colección mutada dejaría que una petición iniciada bajo una configuración terminara bajo otra o fallara en un provider que ya no existe. Esto es lo que hace que el congelado de llamada por paso del seam (`llm.prepareCall()`) se mantenga de principio a fin — cambiar de modelos a mitad de respuesta tiene efecto en el siguiente paso, nunca dentro del que está en vuelo. Las peticiones llegan a su provider a través de `Models.streamSimple()`. Una ruta de catálogo que conserva su protocolo de catálogo **reutiliza** el provider instalado con su lista de modelos sustituida, porque ese provider posee implementaciones de API que este paquete no puede reconstruir — Bedrock carga su módulo Smithy a través de un punto de entrada separado — así que reconstruirlo a partir de piezas estrecharía en silencio qué providers funcionan. Cualquier otra ruta la construye `createProvider()` sobre la tabla de protocolos que hay detrás de `supportedProtocols()`, cuyas entradas son las mismas fábricas que usan las propias fábricas de providers de pi-ai.

La clave `apiKeyEnv` de una ruta sigue resolviéndose a través del seam del harness antes de que la petición llegue a pi-ai y viaja como la opción `apiKey` de la petición, que pi-ai trata como el override de auth de mayor prioridad — la semántica de referencia que falla en voz alta sigue siendo del harness. Bajo ese override, la colección lleva el almacén de credenciales de este plugin y el contexto de auth ambiental: un sign-in almacenado (una concesión OAuth, o una clave escrita en el propio prompt de login de pi-ai) autentica su ruta a través de ellos y se refresca a sí mismo bajo el lock entre procesos del almacén. El almacén direcciona los registros como `llm-pi-ai/<provider id>`, y una clave de ruta declarada a mano fuera de esa gramática de registros (mayúsculas, puntos, guiones bajos) se lee como que no guarda nada almacenado y no como un error de direccionamiento; una ruta así no puede recibir sign-in — una escritura de registro para ella se rechaza con `LlmError('UNSTORABLE_PROVIDER_ID')` — y autentica vía `apiKeyEnv` o ajustes ambientales del provider. Una ruta que no nombra credencial alguna se resuelve como configurada pero sin clave y deja el requisito al protocolo, que es donde vive de verdad.

El descriptor del modelo seleccionado suministra la implementación del protocolo. Esto incluye diferencias nativas de API como los modelos de OpenAI cuyo descriptor usa la API Responses en lugar de Chat Completions; el adaptador del harness no fija en código la selección de endpoint por nombre de modelo.

Las respuestas de assistant correctas almacenan un estado de replay JSON sin pérdida y versionado junto al provider y el modelo que las produjeron, como un `ReplayEnvelope`: una mitad a nivel de respuesta (kind, version, API, ruta, ids de respuesta, motivo de stop nativo) más una entrada por bloque por cada bloque transmitido que lleva las firmas de ese bloque. La alineación por bloque es lo que `BlockAssembler` poda cuando el ensamblaje descarta un bloque (una llamada de herramienta de `max-tokens`), de modo que las entradas almacenadas describen siempre el contenido almacenado — los bloques retenidos conservan sus firmas. En el momento de la petición, `LlmRuntime` pasa el estado de replay solo cuando la ruta histórica del provider y la ruta objetivo del provider están actualmente poseídas por esta misma instancia de `PiAiAdapter`. El adaptador valida el estado y restaura los ids de respuesta de pi-ai y las firmas de provider incluso cuando cambian el provider o el modelo objetivo; pi-ai decide entonces qué metadatos puede reutilizar su API objetivo. La historia sin estado de replay se traduce como contenido extranjero neutral respecto al provider y nunca suplanta una respuesta nativa de pi-ai.

El contenido duradero es el registro autoritativo; el estado de replay solo restaura la fidelidad nativa. Un estado almacenado que esta build no puede usar — el kind de otro adaptador, otra versión (incluida la forma plana pre-envelope que llevan los logs antiguos), metadatos malformados, desajustes de provider/modelo entre el mensaje y el estado de replay, o desajustes de contenido/bloques — degrada ese único mensaje de assistant a la misma conversión extranjera neutral respecto al provider en lugar de fallar la petición, y el plugin registra el diagnóstico `INVALID_REPLAY_STATE` a través de su hook `onReplayDegrade`.

## Diferencias de vocabulario

- Los argumentos de llamadas de herramienta de pi-ai son objetos parseados; el harness almacena cadenas JSON en bruto. El adaptador parsea la entrada y vuelve a serializar la salida.
- pi-ai informa de los fallos como eventos de error en el stream; estos se mapean a chunks `finish {kind:'error'|'aborted', failure}`. El texto de error específico del provider distingue el `QUOTA` terminal del `RATE_LIMIT` transitorio, mientras que las señales de texto y de uso evaluadas contra la ventana de contexto del modelo resuelto normalizan el desbordamiento a `CONTEXT_WINDOW_EXCEEDED`. Un `stop` terminal cuyo mensaje no lleva bloques de contenido se mapea a un `finish {kind:'error'}` con código `EMPTY_RESPONSE` (reintentado por la política por defecto) en lugar de un mensaje vacío con éxito.
- pi-ai pliega los tokens de razonamiento en el uso de salida; no hay un conteo separado de razonamiento que mapear.
- El nivel de pensamiento `off` de pi-ai cruza el seam de capacidades del Harness sin cambios y se convierte en una opción común `reasoning` de pi-ai omitida en el despacho.
- `GenerateOptions.stop` se rechaza con `UNSUPPORTED_OPTION` porque la UI común de streaming de pi-ai no puede garantizarlo entre providers.

## Atribución de app

Cada petición lleva la cabecera de atribución compartida de `attributionHeaders()` de dsh-llm, fusionada a través de la opción `headers` de stream de pi-ai. No se sintetizan cabeceras de atribución de app específicas del provider. Ver [dsh-llm § Atribución de app](../llm/README.es.md#app-attribution-attributionts).

## Peso de dependencias

pi-ai instala varios SDKs de providers y carga perezosamente el que selecciona el modelo del catálogo. El peso de dependencias queda aislado en este paquete de adaptador opcional.

## Experiencia de modelo

### Petición al provider a través de pi-ai

#### Lo que ve el modelo

El modelo de catálogo seleccionado recibe `GenerateOptions.system`, la historia, las herramientas y los campos de muestreo soportados por la API común de streaming de pi-ai. Cada imagen retenida va precedida de texto estable que nombra su id completo de adjunto y sus dimensiones reales de petición. Cuando el payload base64 de imágenes acumulado supera el `maxRequestImageBytes` de la ruta, cada imagen descargada (la más antigua primero) se sustituye por texto fijo que le dice al modelo que vuelva a leer el archivo cuando haya una ruta disponible o que pida al usuario que lo adjunte de nuevo. Los adjuntos normalizados descargados no se leen ni se transforman. Los metadatos de replay nativos del provider solo se restauran cuando el adaptador los valida para el contenido histórico.

#### Efecto en tokens

La tokenización del provider gobierna la entrada exacta. Las imágenes retenidas añaden el adjunto estable y el descriptor de coordenadas; el marcador de descarga sustituye los tokens visuales de una imagen omitida. Los metadatos de replay pueden permitir que una API nativa reutilice el estado del lado del provider.

#### Efecto en la caché KV

La conversión conserva el orden lógico de la petición sin añadir texto, mientras que la serialización del provider seleccionado y el estado de replay determinan la reutilización. Cambiar la instancia del adaptador, el provider, el modelo o cualquier token de petición upstream puede impedir la reutilización desde la primera diferencia. Cruzar el límite de imágenes reescribe un mensaje temprano (la imagen recién descargada se convierte en texto de marcador), así que la reutilización termina en ese mensaje hasta que el prefijo descargado se estabiliza.

### Respuesta del provider

#### Lo que ve el modelo

Los eventos de pi-ai se convierten en chunks de razonamiento, texto, llamadas de herramienta, uso y finish del harness. El adaptador pasa los argumentos de herramienta parseados al harness como cadenas JSON en bruto.

#### Efecto en tokens

El contenido generado afecta a las entradas posteriores solo después de que el loop lo registra. pi-ai pliega los tokens de razonamiento en el uso de salida cuando el provider no los informa por separado.

#### Efecto en la caché KV

El contenido de respuesta registrado se añade a la siguiente petición y no invalida su prefijo reutilizable anterior. Los metadatos de transporte no registrados y la contabilidad de uso no afectan a la identidad de la caché.

## Limitaciones conocidas y trabajo diferido

- **`maxRequestImageBytes` solo cuenta el payload base64 de imágenes** — el texto, las herramientas, los descriptores y la estructura JSON viajan fuera del límite, así que debe situarse por debajo del tope del cuerpo de petición del gateway con margen. La descarga es una proyección determinista de la petición y no se registra como evento de sesión.
- **Un sign-in vive solo en el proceso que lo inició** — un intento de autorización no es duradero, así que recargar la página a mitad del login lo abandona y la persona empieza de nuevo. Cerrar sesión es `deleteRecord` sobre el registro almacenado, que lo olvida localmente sin avisar al emisor.
- **El descubrimiento nativo del provider responde a través del contexto ambiental de este plugin** — una ruta que no nombra credencial difiere a la resolución propia del provider del catálogo, que pide valores de entorno (`AZURE_OPENAI_API_KEY`, `AWS_PROFILE` y el conjunto propio de cada provider) y archivos de credenciales locales. Ambas preguntas se responden aquí: el seam de credenciales se consulta antes que el entorno del proceso, y la existencia de archivos se comprueba contra el filesystem del proceso anfitrión con `~` expandido. Lo que no puede hacer es *leer* el contenido de un archivo de credenciales — un provider que parsea `~/.aws/credentials` por sí mismo lo hace directamente, fuera del seam.
- **Los ajustes pueden añadir o sobrescribir rutas, no eliminar rutas de composición** — la capa de usuario se fusiona sobre la `base` de la composición, así que eliminar un provider suministrado por `cordis.yml` es un cambio de composición; `replace` sobre el namespace solo reinicia la capa de usuario.
- **La fusión en capas no tiene borrado para claves de dict** — el seam de ajustes fusiona la `base` de la composición y la capa de usuario por clave, recursivamente, así que un nivel de `reasoningEfforts`, una entrada de `modelOverrides` o un campo `compat` que declara la base no pueden eliminarse desde la capa de usuario, solo sobrescribirse — y para `reasoningEfforts` la ausencia *es* el significado («no ofrecido»), así que un nivel declarado en la base sigue ofreciéndose. Esto solo se dispara cuando la config de una entrada `cordis.yml` declara campos de razonamiento por modelo para el mismo modelo que edita la capa de usuario; la postura soportada es dejarlos al documento de ajustes (la composición distribuida monta el adaptador dormido), y una lista `models` es un array que sustituye por completo, que es la salida en banda.
- **`headers` puede llevar una credencial que el redactor nunca ve** — el dict `headers` del perfil son cadenas planas, así que un `Authorization` o `api-key` fijado ahí lo devuelve tal cual un `describe()` redactado y lo renderiza cualquier UI de configuración. Almacena las credenciales como referencias `apiKeyEnv`; hacer el dict de solo escritura se difiere con el resto del [trabajo de frontera wire](../llm/README.es.md#known-limitations-and-deferred-work).
- **El catálogo de una ruta nunca se actualiza a sí mismo** — el catálogo es lo que diga `settings.yaml`, así que una lista de modelos está tan al día como su última edición. Nada de aquí consulta a un provider por los modelos que sirve; una ruta gana un modelo cuando alguien lo escribe.
- **Un protocolo wire por ruta** — `api` se aplica a toda la ruta, así que una ruta de catálogo de protocolo mixto (un catálogo estilo OpenAI que abarca Responses y Chat Completions) no puede alojar un modelo del otro protocolo, y añadir un modelo que esa ruta no describe exige nombrar `api` y mover a todos los modelos a él. Dividir el provider entre dos claves de ruta es el workaround.
- **Una declaración de modalidad no se verifica** — nada interroga a un endpoint sobre lo que acepta, así que un modelo que declara `image` y que su gateway no sirve es rechazado por el provider después de la admisión del prompt. La imagen duradera permanece en la historia y el mismo modelo mal declarado puede volver a fallar. Cambiar a un modelo solo de texto sigue siendo posible porque el runtime de LLM compartido proyecta las referencias de imagen en texto estable para esa petición exacta.
- **Una ruta sin autenticar depende de su protocolo** — no nombrar credencial resuelve la ruta como configurada pero sin clave, pero la implementación compatible con OpenAI de pi-ai sigue exigiendo una API key o una cabecera `Authorization`, así que un servidor local sin clave necesita una credencial de marcador referenciada por `apiKeyEnv` o una entrada `Authorization` en `headers`.
- **`GenerateOptions.stop` no está soportado** — las opciones comunes de stream de pi-ai no pueden garantizar el comportamiento de secuencia de stop entre providers, así que el adaptador rechaza el campo.
- **Los mensajes `system` en la historia usan la conversión de contexto común de pi-ai** — la colocación específica del provider sigue a pi-ai y no a un override wire propiedad del harness.
- **El estado HTTP del provider no está disponible** — los eventos de error de pi-ai no exponen un estado HTTP estable entre providers; los fallos exponen solo códigos de error estables del harness.
- **La política de reintentos es propiedad del provider, no un reintento del SDK** — cada perfil de provider puede suministrar un `retryPolicy` anidado; la omisión se resuelve al modo normal con cinco reintentos, y la política efectiva de la ruta es la que `dsh-llm-retry` ejecuta en el punto de extensión de paso fallido del agent. Los reintentos del SDK de pi-ai permanecen deshabilitados para que los pasos de agent duraderos y los eventos `llm/retry` sean dueños de cada intento visible, y las llamadas directas a `ctx.llm.stream()` sigan siendo de un solo intento.
