# @deepseek-ai/dsh-sandbox-windows-acl

[English](README.md) | Español

Backend de sandbox de restricción de escritura en Windows para el [seam de sandbox del harness](../sandbox/): un port Node.js/[koffi](https://koffi.dev/) del mecanismo de [huoyaoyuan/windows-acl-restrict-poc](https://github.com/huoyaoyuan/windows-acl-restrict-poc) (`10e4dfb`, la revisión fijada), montado como el rung win32 con `enforcement: 'partial'` de la cadena [`@deepseek-ai/dsh-sandbox-local`](../sandbox-local/) (modos `workspace-write` / `read-only`); el mismo paquete lleva los backends de Linux/macOS.

El mecanismo en una línea: el token del llamante se duplica en un token `WRITE_RESTRICTED` cuyos SIDs restrictivos llevan capacidades separadas de workspace y de temp privado. El SID de workspace se deriva de forma determinista de la ruta canónica del workspace (`workspaceWriteSid`), así que el ACE de la raíz del workspace se materializa una vez por workspace y por máquina, y cada sesión, llamada o reinicio posterior acierta con la omisión de ACE exacto. Cada par sesión/workspace vivo recibe en cambio un directorio temp aleatorio y un SID derivado de esa ruta (`tempWriteSid`), de modo que las sesiones comparten la autoridad de workspace prevista sin heredar la autoridad temp unas de otras. Windows concede una escritura solo donde lo permiten a la vez el acceso normal del llamante Y la intersección de SIDs restrictivos. Estos SIDs son las allowlists primarias y no conceden nada en otro lugar, pero la comprobación también hereda los ACE de escritura ambientales de los OTROS SIDs restrictivos (el SID de logon del grupo keep-alive + Everyone), y las ACL de NTFS pertenecen a objetos de archivo, no a rutas; los límites de Everyone y de hard links son la razón por la que el rung informa de enforcement parcial en lugar de completo.

Construir directamente sobre el mecanismo ACL bruto es la decisión de diseño registrada: implementa ambos modos de confinamiento sin los problemas que arrastran las opciones de contenedor rechazadas — consulta la [nota de diseño](../../../.agents/notes/implemented/feature/2026-08-08-windows-acl-restricted-token-sandbox.es.md) ([mxc](https://github.com/microsoft/mxc/blob/main/docs/process-container/os-version-support.md) exige un piso de SO de Windows 11 24H2 y escrituras masivas de DACL del host para lecturas de rutas arbitrarias; AppContainer no puede hacer lecturas de rutas arbitrarias en absoluto).

## Uso

```ts
import { mkdtempSync, rmSync } from 'node:fs'
import { tmpdir } from 'node:os'
import { join } from 'node:path'
import { AclSandbox, tempWriteSid, workspaceWriteSid } from '@deepseek-ai/dsh-sandbox-windows-acl'

const workspaceRoot = process.cwd()
const tempDir = mkdtempSync(join(tmpdir(), 'dsh-'))

// mode selects the token's restricting-SID list (see Modes below) and must
// match the grant shape. workspace-write requires distinct workspace and
// private-temp identities; pass tempDir: null to disable temp writes.
const sandbox = new AclSandbox({
  writableDirs: [workspaceRoot],
  tempDir,
  writeSid: workspaceWriteSid(workspaceRoot),
  tempWriteSid: tempWriteSid(tempDir),
  mode: 'workspace-write',
})
await sandbox.init() // throws on ANY Win32 failure — never spawns unrestricted

const child = sandbox.spawn({ command: 'pwsh', args: ['-NoProfile', '-Command', '...'], cwd: workspaceRoot })
const { stdout, stderr, exitCode } = await child.wait()

sandbox.dispose() // revokes the revocable (temp) grant, keeps the standing workspace ACE; reports every cleanup failure
rmSync(tempDir, { recursive: true, force: true })
```

Un `AclSandbox` directo exige un directorio temp privado explícito (o `tempDir: null`; la raíz temp ambiental nunca es una concesión implícita), concede los ACE del workspace de forma STANDING (dispose() los deja — son la caché de reutilización entre instancias) y concede el SID temp distinto de forma revocable. La reutilización del lado del servidor es la clase `AclWriteGrant`: `add(path, standing)` por directorio, `dispose()` revoca las rutas revocables y libera el SID — consulta el contrato del runner más abajo. Cada llamada a la API Win32 de este paquete se comprueba; los fallos lanzan `Win32Error` con el nombre de la API, el código Win32 exacto, el texto de sistema de `FormatMessageW` y la ruta/contexto que falló. Esto es deliberado: el POC ignoraba cada valor de retorno y, cuando `CreateRestrictedToken` fallaba, ejecutaba silenciosamente al hijo con el token completo SIN restricciones (fail-open). Este port falla en fail-closed por construcción.

## El runner de confinamiento

La forma orientada al seam es la **entrada de runner** (`./runner`), el wrapper de prefijo de argv que `@deepseek-ai/dsh-sandbox-local` lanza en lugar del comando del llamante — la misma arquitectura que bwrap/landlock-run/sandbox-exec, así que el contrato `confine()` del seam de sandbox no necesita cambios. Contrato de argv estable:

```sh
node runner.js --workspace <dir> --temp <dir> --mode <read-only|workspace-write> [--write-sid <S-1-4-…> --temp-write-sid <S-1-4-…>] -- <argv...>
```

El runner crea el token restringido, lanza el argv envuelto bajo él con el stdio del llamante pasado directamente (las pipes del llamante, hechas heredables alrededor del spawn — Node limpia la heredabilidad del stdio al arrancar, algo que los spawns brutos deben compensar), envuelve al hijo en un job `KILL_ON_JOB_CLOSE` (un runner muerto mata al hijo), ignora su propio Ctrl+C de consola para que el hijo gestione el suyo, refleja el código de salida del hijo y revoca su concesión temp autogestionada al salir (los ACE del workspace permanecen). Cada fallo del lado del runner imprime `windows-acl-run: <detail>` en stderr y sale con 127 — las `RUNNER_FAILURE_RULES` del seam coinciden con esa firma, así que una negativa del runner nunca se confunde con una denegación.

**Reutilización del workspace y aislamiento del temp**: el seam materializa el ACE del SID de workspace determinista de forma STANDING (una vez por workspace y por vida de servidor, nunca revocado — es la caché de reutilización), y después crea un directorio temp privado aleatorio y un SID revocable distinto para cada par sesión/workspace vivo. Pasa ambas identidades como el par requerido `--write-sid`/`--temp-write-sid`; el runner verifica cada una contra su ruta propietaria y ni concede ni revoca (`manageDacls: false`). Un fork recibe una capacidad temp distinta, y un provider nuevo da incluso a la misma sesión reanudada una ruta y un SID nuevos, así que el residuo de un crash es basura inerte, no una colisión ni una capacidad heredada. Sin el par, `--temp` nombra una raíz: un runner workspace-write sin agent/independiente crea un hijo privado aleatorio, autogestiona su SID temp, reescribe TMP/TEMP y elimina al hijo al salir. Un workspace igual a esa raíz o que la contenga se rechaza antes de cualquier concesión porque su ACE de workspace heredable autorizaría de otro modo a cada hijo privado; la API directa rechaza igualmente el solapamiento entre cualquier raíz escribible y el directorio temp privado real. Re-conceder el ACE de workspace standing tras un reinicio es idempotente: `grantWrite` lee la DACL actual y se salta `SetNamedSecurityInfoW` cuando el ACE exacto ya está presente (esa aplicación re-propaga con avidez el ACE idéntico por todo el árbol — minutos en workspaces grandes). Coste conocido: la primera concesión en un árbol de workspace grande se bloquea por esa propagación ávida una vez por workspace y por máquina.

Modos (la lista de SIDs restrictivos del token sigue al modo; el grupo keep-alive es el SID de logon + Everyone en AMBOS modos — sin ellos, la inicialización temprana de DLL muere con `0xC0000142` y CNG estrella pwsh con `0xE0434352`):

- `workspace-write` (SID de logon, Everyone, SID de workspace, SID de temp): el workspace y el subdirectorio temp PRIVADO de la sesión llevan concesiones Write separadas; el resto de escrituras direccionables por ACL se deniegan salvo los límites documentados de Everyone y de hard links.
- `read-only` (SID de logon, Everyone — SIN SID de escritura): sin concesiones explícitas de write-SID. El write SID se queda FUERA de la lista a propósito: el ACE de concesión standing del workspace de un periodo anterior de workspace-write (una bajada `/permission`, o una sesión reanudada tras crash) permanece INERTE bajo read-only porque la comprobación de pass-2 restringida a escritura concede solo lo que lleva la lista restrictiva — mientras que el ACE standing mantiene la re-subida libre de re-propagación. Los derechos ambientales de Everyone siguen siendo el límite parcial documentado. Las escrituras a NUL son AMBIENTALES, no concedidas: la DACL del dispositivo concede a Everyone read+write+execute (`0x1201BF`), así que los openers cuya máscara encaja (cmd `> NUL`, node `\\.\NUL`) pueden escribir en él en AMBOS modos — el sandbox no puede conceder cero al dispositivo NUL mientras Everyone siga en el grupo keep-alive. `Set-Content NUL` falla en ambos modos (un efecto de la capa de PowerShell/.NET, fijado por la suite de read-only — la DACL del dispositivo no es la parte que deniega); la redirección `> $null` de PowerShell sigue funcionando (descarta sin abrir NUL).

Authenticated Users está ausente de AMBAS listas — la comprobación de seguridad del namespace WMI falla (`0x80041003`), así que los cmdlets CIM y `Get-ComputerInfo` (que devuelve silenciosamente resultados incompletos en lugar de un error) no están disponibles en NINGÚN modo confinado, y el escape de creación de árbol en la raíz C:\ (los ACE standing `AU:(AD)` + `AU:(OI)(CI)(IO)(M)`) está cerrado en ambos — la documentación orientada al modelo enuncia ese contrato, no una promesa de prompt. INTERACTIVE/LOCAL también están ausentes de AMBAS listas: el árbol Public del host concede escritura a INTERACTIVE, así que las escrituras en Public se deniegan — fijado por la regresión de sonda Public escribible ambiental del runner (consulta la nota de diseño).

La clase `AclSandbox` (`tempDir` privado explícito + `tempWriteSid`, o `tempDir: null` para deshabilitar las escrituras de temp) sigue siendo la API programática para spawns directos; `AclWriteGrant` es la mitad de materialización del lado del servidor del ciclo de vida de la concesión.

## Verificación de cabeceras

Todas las constantes, firmas y diseños de struct se verificaron contra las cabeceras de Windows en la máquina de desarrollo (MinGW `winnt.h` / `accctrl.h` / `aclapi.h` / `securitybaseapi.h` / `sddl.h` / `processthreadsapi.h` / `fileapi.h` / `namedpipeapi.h` / `synchapi.h` / `winbase.h`) y se contrastan en runtime mediante [`verify/abi-probe.cpp`](verify/abi-probe.cpp) (tamaños, offsets, valores de enum, static asserts):

```sh
g++ -std=c++20 -municode -O2 -o abi-probe.exe verify/abi-probe.cpp -ladvapi32 && ./abi-probe.exe
```

Las definiciones de struct de koffi afirman sus tamaños contra la sonda al cargar el módulo, así que una deriva de diseño cabecera/koffi falla de forma ruidosa en lugar de corromper memoria.

## Límites verificados (inherentes a los tokens restringidos, no a este port)

- **Las concesiones a Everyone siguen siendo autoridad de escritura ambiental.** Everyone debe permanecer en ambas listas restrictivas: quitarlo rompe la inicialización temprana de DLL y CNG. Un objeto NTFS externo cuya DACL normal concede a Everyone el derecho de escritura solicitado supera, por tanto, ambas comprobaciones de acceso y sigue siendo escribible en ambos modos. La suite del runner real aprovisiona un directorio externo `Everyone:Modify` y fija ese comportamiento; el provider informa de `enforcement: 'partial'` para que los llamantes puedan rechazar o exponer el límite más débil.
- **Los hard links son alias de objeto de archivo, no alias de ruta.** Un ACE de workspace heredable propagado a un hard link NTFS existente cambia el único descriptor de seguridad del archivo subyacente, así que el mismo objeto es escribible a través de un alias externo. Rechazar todo archivo de workspace con múltiples enlaces no es viable para las instalaciones ordinarias de pnpm, que usan hard links hacia su store direccionable por contenido; la suite nativa del runner fija la brecha y el informe parcial del provider nombra su consecuencia.
- **Las escrituras se restringen; las lecturas, la red y la visibilidad de procesos no.** `WRITE_RESTRICTED` intersecta solo los accesos de escritura, así que un hijo confinado puede leer cualquier archivo legible por el llamante y abrir sockets. El modo `read-only`, por tanto, no puede expresarse solo con este mecanismo; combínalo con una política del lado de lectura o con un token de capacidades AppContainer/`S-1-15-2` para un confinamiento más fuerte.
- **El aislamiento de consola no está disponible.** Bajo el token restringido, los hijos creados con `CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE` mueren durante la inicialización de DLL con `STATUS_DLL_INIT_FAILED` (`0xC0000142`). El POC intentó arreglarlo añadiendo el SID de logon de consola (`S-1-2-1`) a la lista restrictiva; en Windows 11 26200, `CreateWellKnownSid(WinLocalLogonSid)` falla con `ERROR_INVALID_PARAMETER` (87), el `WinConsoleLogonSid` correcto produce un `S-1-2-1` válido pero el hijo sigue muriendo, y la revisión final del POC eliminó tanto el SID como el aislamiento de consola. Los hijos comparten, por tanto, la consola del host; la redirección de stdio se basa en pipes y no se ve afectada.
- **Las concesiones de ACL son mutaciones standing de directorios.** Persisten si el proceso muere a mitad de ejecución; los ACE del workspace son standing POR DISEÑO (nunca revocados — la caché de reutilización), los ACE de temp los revoca `dispose()` (`init()` también revoca una concesión de temp ya aplicada cuando falla un paso posterior). La limpieza manual documentada del POC (`icacls <dir> /remove '*S-1-4-…'`) falla en esta plataforma con `ERROR_NONE_MAPPED` (1332) — revoca a través de este módulo en su lugar. Un cierre sucio no necesita auto-reparación para el ACE del workspace: el SID derivado vuelve a acertar con el ACE standing en la siguiente provisión (saltándose la aplicación); el ACE de write-SID nunca acumula una segunda identidad por reinicio porque la identidad ES el workspace.
- **Los directorios concedidos deben pertenecer al llamante.** El `WRITE_DAC` implícito del propietario es lo que permite al sandbox editar la DACL sin elevación.
- **La raíz temp ambiental nunca se concede implícitamente.** Un llamante workspace-write de `AclSandbox` directo debe aportar un `tempDir` privado existente más su `tempWriteSid` distinto, o deshabilitar explícitamente las escrituras de temp con `tempDir: null`. El directorio temp real debe ser disjunto de toda raíz escribible. El seam crea un directorio privado aleatorio; las llamadas de runner sin agent tratan `--temp` como la raíz padre y crean su propio hijo aleatorio, pero rechazan un workspace igual a ese padre o que lo contenga antes de cualquier mutación de ACL.
- **La capacidad temp del hijo confinado es privada por par sesión/workspace vivo.** El runner reescribe TMP/TEMP mediante `SetEnvironmentVariableW` hacia ese directorio privado antes del spawn y el hijo hereda el bloque reescrito (semántica de bwrap `--tmpfs /tmp`). El ACE y el directorio de temp se eliminan al disponer el provider, o después de cada invocación sin agent. Un crash puede dejar basura `%TEMP%` inerte, pero un provider reanudado elige una ruta y un SID nuevos en lugar de colisionar con el residuo o reautorizarlo. La suite nativa del runner demuestra que dos tokens que comparten el mismo SID de workspace no pueden escribir en los directorios temp del otro.
- **`whoami` y los cmdlets de inspección de token fallan bajo el token restringido.** `GetTokenInformation` sobre la copia no está parcialmente disponible para el hijo, así que `whoami /all` informa de errores — ruido diagnóstico del esquema de restricción, no un fallo operativo; las superficies de denegación que importan (escrituras de archivo) no se ven afectadas.

## Limitaciones conocidas y trabajo aplazado

- **Una allowlist de escritura por workspace** — el write SID es la unidad de la allowlist y ES la identidad del workspace; reutilizar una instancia de sandbox en dos workspaces amplía ambas concesiones a ambas raíces (el mismo SID nombraría entonces dos raíces). Crea una instancia por raíz de workspace — el seam hace exactamente esto, con clave por ruta de workspace.
- **La limpieza es best-effort por diseño** — `dispose()` intenta cada revocación de temp y agrega los fallos en un `AggregateError`; un fallo de limpieza puede dejar atrás el directorio aleatorio y su ACE solo de temp-SID. Una vez que el proceso sale, ningún token futuro lleva ese SID, así que el residuo es inerte hasta que la higiene de temp del SO o la eliminación manual del directorio lo reclamen.
- **Los ACE de workspace standing son residuo invisible.** Renombrar un workspace deriva un SID nuevo; los ACE antiguos de la ruta antigua permanecen (inertes, solo de write-SID). Un futuro comando de limpieza puede cosecharlos; nada se re-propaga por culpa de ellos.
- **Los directorios con DACL NULL no preservan la identidad bajo concede+revoca.** Un directorio con DACL NULL (raro — los directorios creados por Windows llevan DACL reales) significa «control total para todos»; `grantWrite` construye la nueva ACL desde ese null, y el round-trip de revocación deja una DACL VACÍA (deniega todo) en lugar de la DACL NULL original. El POC comparte el comportamiento; los directorios reales de workspace y temp llevan DACL reales, así que esto sigue siendo un caso límite documentado, no un camino protegido.
- **La captura de stdio por pipe es imposible para los nietos confinados (la plantilla SD por defecto de named pipes).** El stdio de pipe de libuv usa NAMED pipes; `CreateNamedPipeW` sin atributos de seguridad instala la plantilla SD por defecto en modo usuario de la capa Win32 (construida por KernelBase — owner/SYSTEM/Admins con control total, Everyone/ANONYMOUS solo lectura, la plantilla fija que [documenta MS](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)) — NO la DACL por defecto del token, que es lo que el kernel aplica a una creación bruta con SD null — así que el extremo cliente abre pidiendo acceso de escritura que ningún SID restrictivo concede: `spawn(..., { stdio: 'pipe' })` dentro de un proceso confinado falla con EPERM, el límite de «sin redirección de salida» documentado por el POC para los tokens WRITE_RESTRICTED. Los spawns de stdio heredado (`inherit`/fd) e ignorado (`ignore`) funcionan, y los anonymous pipes (CreatePipe — un consumidor de DACL por defecto del token, p. ej. los pipelines de PowerShell) funcionan porque la DACL por defecto del token restringido lleva un ACE de SID restrictivo con acceso total (fijado en init). Un proceso confinado no puede, por tanto, capturar la salida de un nieto a través de un pipe; las herramientas que deben capturar salida no pueden ejecutarse confinadas.
- **La materialización de la concesión es una propagación ávida por todo el árbol.** `SetNamedSecurityInfoW` sobre un directorio con ACE heredables recorre cada descendiente de inmediato (NO perezosamente por acceso — medido en decenas de segundos en árboles de workspace grandes). La identidad por workspace lo paga una vez por workspace y por máquina (perezosamente en la primera ejecución confinada de la historia, omitida por completo en cada provisión posterior cuando el ACE exacto está presente). Los directorios temp privados empiezan vacíos, así que su concesión distinta es barata. Si un workspace es enorme, la primera escritura confinada en este host es correspondientemente lenta.
- **El confinamiento del lado de lectura y la política de red están fuera de alcance** — `WRITE_RESTRICTED` intersecta solo los accesos de escritura; combina este backend con una política del lado de lectura para un confinamiento más fuerte.
- **Las advertencias de directorios anchos y volúmenes FAT están aplazadas; los objetivos clase FAT siguen siendo escribibles.** Las advertencias del lado de UI por conceder directorios inusualmente anchos o volúmenes clase FAT (sin ACL) aún no están implementadas, y un volumen FAT como RAÍZ de la concesión simplemente hace fallar la concesión de forma ruidosa (sin soporte de ACL). Un objetivo clase FAT FUERA de las raíces concedidas es distinto: no tiene descriptores de seguridad, así que la comprobación de escritura del token restringido pasa (Everyone está en ambas listas) y esos objetivos son escribibles bajo AMBOS modos confinados. FAT se trata como residuo heredado — sin soporte y sin ingeniería alrededor; esta postura de solo-advertir se documenta aquí en lugar de mitigarse.
- **El modo de lenguaje de PowerShell difiere según el modo confinado.** Bajo `read-only`, PowerShell no puede crear sus archivos de sonda AppLocker en temp y arranca conservadoramente en ConstrainedLanguage: `Add-Type` (compilación C#, P/Invoke), las llamadas estáticas .NET no núcleo (`[System.IO.*]::`, `[math]::`, `[Environment]::`), los objetos COM y la reflexión fallan con errores `Cannot create type` / `Cannot invoke method` («solo tipos núcleo»), y `$ExecutionContext.SessionState.LanguageMode = 'FullLanguage'` se rechaza. Bajo la ruta `workspace-write` distribuida, la capacidad de temp privado permite que esa sonda se complete, así que pwsh permanece en FullLanguage salvo que la política WDAC/AppLocker de todo el host diga lo contrario; un `AclSandbox` directo configurado con `tempDir: null` no tiene esa garantía y puede fallar la sonda en fail-closed como read-only. Esta división es comportamiento de arranque de PowerShell, no parte del límite de escritura de ACL. La descripción de la herramienta `pwsh` enseña los modos distribuidos al modelo; las llamadas `danger-full-access` se ejecutan sin confinar en FullLanguage.
