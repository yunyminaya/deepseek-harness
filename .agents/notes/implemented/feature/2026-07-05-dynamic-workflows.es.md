# Agent Note: Workflows dinámicos — un seam de orquestación multiagente dirigido por script

Status: implemented

[English](2026-07-05-dynamic-workflows.md) | Español

## Problema

El harness puede delegar UNA tarea a UN hijo (`dsh-tool-subagent`), pero el trabajo que se ramifica en muchas piezas independientes — una auditoría sobre muchos archivos, una migración, investigación desde múltiples ángulos, verificación adversarial de hallazgos — fuerza al modelo a orquestar turno a turno: cada resultado intermedio aterriza en el contexto del padre, el plan no vive en ningún sitio durable y la coordinación cuesta un round-trip de modelo por paso. Claude Code entrega esta capacidad como [workflows dinámicos](https://code.claude.com/docs/en/workflows): el modelo escribe un script JavaScript de orquestación, un runtime lo ejecuta, y el script — no la conversación — sostiene el bucle, la ramificación y los resultados intermedios.

## Decisión

Una familia de capacidad de workflow en `packages/workflow/` con la forma del seam de bash (Service Definition / Service Provider / Consumer), más la fundamentación de salida estructurada que necesita en el seam de subagente.

### El contrato del script (compatible con Claude Code)

Una llamada de workflow contiene `meta` JSON (`name`, `description` y `whenToUse`/`phases` opcionales) y un cuerpo `script` JavaScript con `await` de nivel superior que retorna un valor JSON. Los metadatos se validan como datos y jamás se evalúan. El cuerpo recibe `agent(prompt, options)`, `parallel(thunks)`, `pipeline(items, ...stages)`, `phase(title)`, `log(message)` y `args`. Las etapas del pipeline reciben `(prev, item, index)` sin barrera entre etapas; los hijos fallidos y los errores ordinarios de etapa resuelven el elemento afectado a `null` y se saltan sus etapas restantes. Las restricciones de determinismo de Claude Code quedan aplazadas junto con el journaling, de modo que los cuerpos compatibles pueden usar reloj y aleatoriedad tras mover su cabecera meta al parámetro.

Una divergencia de rigor deliberada frente a CC: el mal uso de los hooks — opciones desconocidas o aplazadas (`effort`/`isolation`/`agentType`), argumentos malformados, schemas fuera del subconjunto soportado, topes disparados, fallos de arranque del seam — lanza un `WorkflowError` con `fatal: true`, y los combinadores RELANZAN los errores fatales en lugar de nullear el elemento. Sin esto, una opción con errata se disuelve en un `null` indistinguible de un fallo de hijo — el modo de fallo aceptado-y-luego-ignorado que este repositorio prohíbe. Una adición: el parámetro `args` de la herramienta es un OBJETO JSON (una lista desnuda se envuelve como campo) para que el schema del cable se mantenga honesto.

### El seam (dsh-workflow)

`ctx.workflowEngine` es un `WorkflowEngine` abstracto con la forma de bash — un motor por contexto, sin registro de providers con nombre (los motores son reemplazos de despliegue, no coinquilinos). `start(request)` lanza síncronamente ante un script que no puede comenzar; el `result` de un `WorkflowRun` retornado NUNCA rechaza (los fallos se resuelven como `stopReason: 'error' | 'cancelled'`). Los eventos `workflow/*` son emits de solo observación que portan INSTANTÁNEAS DE DATOS (id + meta; `workflow/end` omite el valor del resultado), contenidos por listener, a imagen de `subagent/start`/`subagent/end` — el control queda con el titular de la ejecución. Detalles del vocabulario: [subsystems/workflow.md](../../../../docs/subsystems/workflow.es.md).

### El motor (dsh-workflow-worker-thread): un worker thread por ejecución

**Premisa de confianza**: los scripts de workflow tienen la misma confianza que el acceso bash del modelo. El motor contiene los scripts con bugs y garantiza resultados liquidados, valores JSON-seguros y quietud de cancelación; no se defiende de código hostil. Un contexto vm y un worker thread no son fronteras de seguridad: un script puede escapar hacia las APIs de Node con autoridad sobre todo el proceso. El sandboxing requiere un motor de proceso separado o de isolated-vm detrás de este seam.

**Por qué `node:worker_threads`**: cada ejecución recibe un worker sin pool. Un contexto vm limita la API documentada del script, mientras que un RPC por message-port tiende un puente desde `agent()` hacia los loops hijos del lado del host. El worker evita que el trabajo síncrono del script bloquee el host, provee una frontera de serialización y permite la terminación forzada tras la cancelación. Se rechazó `isolated-vm` por su estado de mantenimiento y sus requisitos de despliegue.

El host valida los metadatos y parsea el cuerpo antes de la publicación. Mapas de payload con clave enum privada definen el protocolo del cable; los arranques pendientes, los registros de hijos publicados, una única señal de cancelación, la recolección de muertes de worker, la precedencia de resultados y la quietud de disposal preservan a través de todo ello el contrato de ejecución de subagente. La [Agent Note de diseño runtime del ámbito de agent](../architecture/2026-07-12-agent-scope-runtime-design.es.md#workflow-children-are-pending-starts-or-published-records) posee esos algoritmos de carreras.

El motor expone una vía de prueba `MessageChannel` en proceso porque la cobertura V8 del proceso principal no ve la ejecución del worker.

**Meta son datos**: el campo `meta` validado por schema llega al seam como JSON y solo se valida en su forma. El host jamás evalúa un literal de metadatos, lo que dejaría correr accessors controlados por el script fuera del aislamiento del worker.

**Frontera de valores**: `materializeFromRealm` copia los valores salientes y rechaza funciones, símbolos, `undefined` anidado, prototipos exóticos, ciclos, arrays ralos y números no finitos. Las copias por propiedad de datos hacen seguro el `"__proto__"`; los getters se leen con normalidad y un getter que lanza falla ruidosamente. `args` cruza a través de `workerData` y se clona de nuevo antes de la exposición. Las funciones del realm se invocan en lugar de copiarse, y los valores lanzados usan un renderizador total para que `result` no pueda rechazar. Los errores de hook son `WorkflowError`s del realm del host, así que los scripts ramifican por `name` o `code` y no por `instanceof Error`, como documenta el README del motor. Los límites de concurrencia, de agent total, de elemento, de timeout y de gracia son configuración validada.

### El Consumer (`dsh-tool-workflow`)

Una herramienta `workflow` que refleja la forma síncrona de `dsh-tool-subagent`: arrancar, esperar, disponer en `try/finally`, puente de abort con `exec.signal`, y no-`completed` → `isError`. Intención de render: una tarjeta `generic` titulada por el parámetro `meta.name` de la llamada (la presentación es una función pura de los args). La descripción de la herramienta ES la especificación de autoría orientada al modelo. La política de uso se entrega con la herramienta como su propia sección de prompt `tool:<toolName>` (guía de solo-pregunta-explícita — la guía de herramientas vive en plugins de herramienta, nunca en la persona de despliegue); el harness no tiene ninguna compuerta de effort estilo ultracode.

Para una ejecución de herramienta de nivel superior, el mismo Consumer escribe también la ejecución y el ciclo de vida real de los miembros en la Session padre llamante como cuatro eventos solo-log `tool-workflow/*`. La vía de registro observa en lugar de controlar la ejecución: su primer fallo de append desactiva las escrituras posteriores de esa ejecución y deja un prefijo legal sin cambiar el resultado de la herramienta. [`ui-workflow-run`](../../../../packages/client/ui-workflow-run/README.es.md) reconstruye esos hechos a través del motor de Conversation Node como una fila Chat con clave propia; la fila genérica de herramienta existente sigue siendo su propia propietaria de presentación. La decisión detallada de persistencia, replay, despliegue y navegación en vivo vive en [ejecuciones de workflow durables en Chat](2026-08-10-durable-workflow-runs-in-chat.es.md).

### La fundamentación: salida estructurada en el seam de subagente

`SubagentStartRequest.outputSchema` lo implementa `dsh-subagent-in-process-driver` para ambos backends en proceso. Cada hijo estructurado recibe sus propios registros de herramienta de captura, instrucción y ejecución con ámbito en `child.ctx`; los hijos concurrentes pueden usar schemas distintos sin compartir política mutable, y disponer el hijo elimina el adjunto completo.

Un schema de salida hace obligatoria una captura comprometida y válida por schema para el éxito del hijo. El runtime con ámbito presenta la herramienta y la instrucción de captura, compromete solo un desenlace final exitoso — incluido el desenlace `run_code` que lo envuelve en una llamada SDK —, deniega los efectos secundarios posteriores una vez la captura queda pendiente, y detiene el hijo sin otro paso de modelo tras el compromiso. Un fallo de validación sigue siendo un error de herramienta reintentable; la finalización limpia sin captura comprometida se liquida como error.

`ObjectJsonSchema` es la vista de Consumer con raíz de objeto del subconjunto unificado y ejecutable de JSON Schema puro en `dsh-tools`; las palabras clave no soportadas fallan ruidosamente porque esos datos del cable se convierten verbatim en los parámetros de la herramienta de captura. La [Agent Note del DSL unificado de schema de valor JSON](../architecture/2026-07-20-unified-json-value-schema-dsl.es.md) posee el vocabulario y la semántica de validación, mientras que la [Agent Note de diseño runtime del ámbito de agent](../architecture/2026-07-12-agent-scope-runtime-design.es.md#structured-output-commits-only-authoritative-outcomes) posee los algoritmos de ensamblaje, compromiso, guardia y parada terminal.

## Pruebas

La lógica del lado del worker corre a través de un `MessageChannel` en proceso para que la cobertura V8 la mida. Las pruebas unitarias cubren los helpers de script, los fallos fatales y anulables, las fronteras JSON, los topes, la cancelación, la propiedad de los hijos y la salida estructurada a través de loops reales. Un smoke de binario compilado corre el `lib/worker.cjs` empaquetado por separado bajo Node plano, un e2e con clave conduce hijos reales, y el comportamiento del workflow orientado al modelo tiene cobertura de instantáneas a través de su ejemplo propietario.

## Aplazado (no-objetivos documentados)

- **Colección en segundo plano** (herramienta de arranque → id de ejecución → aviso de finalización → recolección), diseñada junto con la unificación de shell/subagente en segundo plano.
- **Journaling + reanudación** (`resumeFromRunId`, prefijos de agent() cacheados) — implementarlo reintroduce las prohibiciones de determinismo de CC como un endurecimiento del contrato de script (los scripts hoy pueden leer el reloj).
- **Workflows guardados/empaquetados** (un registro `.deepseek/workflows/`, API de slash-command) y **persistencia del script a un directorio de ejecución** (el evento tool-call ya registra el script de forma durable).
- **`workflow()` anidado**, **`budget` de tokens** y las opciones de agent `effort`/`isolation`/`agentType` (cada una rechaza ruidosamente con un mensaje que la nombra como aplazada).
- **Un timeout de reloj total de la ejecución** — la cancelación siempre libera al llamador (el resultado se liquida dentro de la gracia), así que un tope al tiempo total de ejecución es una perilla de política para el rediseño del segundo plano, no una necesidad de corrección aquí.
- **Endurecimiento del motor más allá de worker threads**: un motor de isolated-vm o de proceso separado detrás del mismo seam (sandboxing real; límites de memoria).
- **Salida estructurada del backend ACP** y **`toolFilter`** (ambos siguen con la capacidad desactivada `false`).

## Alternativas consideradas

- **Contención de valores hostiles en el host** (rechazo de proxies sin traps, recorridos de descriptores con accessors-jamás-invocados, pre-renderizado en el realm de los valores lanzados, promesas/arrays/clones de error construidos en el realm con reconocimiento estructural de fatales): rechazada porque cada defensa apunta a un autor que la premisa de confianza ya acepta, mientras que la frontera de serialización del hilo ya hace totales por construcción los valores entre realms.
- **Ejecución en proceso con `node:vm`**: mecánicamente lo más simple — sin RPC, sin hilo — pero `start()` bloquearía al llamador durante la porción síncrona inicial del script, un giro síncrono más allá del primer await no puede matarse en proceso (el `timeout` de la vm cubre solo esa primera porción), y `dispose()` solo podría abandonar un script sin liquidar sobre el loop del host. El motor de worker thread conserva la misma API de script con contexto vm mientras desbloquea el host y hace real la terminación.
- **Ejecución en segundo plano como default** (la forma de CC): aplazada; el primer plano síncrono coincide con el corte de `dsh-tool-subagent`, y la semántica de segundo plano debe diseñarse UNA sola vez entre shell/subagente/workflow y no por herramienta.
- **Parseo JSON en la capa de workflow para `agent({schema})`**: duplicaría una preocupación del seam en un Consumer mientras el flag de capacidad del seam seguía deshonestamente en `false`.
- **Meta embebida en el script como `export const meta = {...}`** (el formato exacto de CC): mantiene los scripts autocontenidos y los scripts CC listos para usar, pero obtener la meta requiere evaluar texto escrito por el modelo en el host. Ni siquiera un contexto vm vacío y con tiempo puede acotar getters controlados por el script cuando el host lee el objeto resultante. Un parámetro JSON elimina el escáner, la evaluación y el agujero de giro-del-host; el coste es que la cabecera meta de un script CC debe moverse al parámetro (el cuerpo sigue siendo listo-para-usar).
- **`ValueSchemaSpec` como tipo de cable de `outputSchema`**: la forma de autor tiene ahora vocabulario equivalente, pero un workflow aporta datos de JSON Schema puro ajenos al realm; fingir que ese dato de runtime es una declaración de autor de confianza se saltaría la frontera de aserción de schema puro.
- **Una librería de objetos-schema (zod, o la schemastery del repositorio) para el subconjunto de salida estructurada**: el schema es dato de cable — JSON puro que cruza la frontera del realm vm en `agent({schema})` y aterriza verbatim en los parámetros de la herramienta forzada — exactamente donde los objetos-schema vivos no pueden estar; consumir JSON Schema puro en runtime necesitaría un conversor de terceros encima (el núcleo de zod solo emite JSON Schema, no lo inverso), y pondría un segundo lenguaje de schemas junto al rol de configuración de schemastery.
- **ajv para la validación de valores**: valida JSON Schema COMPLETO, así que la compuerta del subconjunto — el punto real del módulo, ya que cada palabra clave aceptada debe ser una que el harness ejecuta — seguiría escrita a mano de todos modos; compila validadores a través de `new Function`; y sería la primera dependencia de runtime de dsh-tools, todo para reemplazar el caminante de valores de ~70 líneas mientras el reporte de errores cualificado por ruta y de toda-violación seguiría siendo de todos modos artesanal.
- **Modo JSON del provider en lugar de la herramienta de captura:** garantiza JSON válido, no conformidad con el schema, y su interacción con las llamadas de herramienta no está clara. La herramienta de captura preserva los reintentos de validación dentro del turno. Los schemas estrictos del lado del provider pueden luego estrechar el subconjunto aceptado sin cambiar este diseño.

## Consecuencias

Los planes ramificados viven ahora en scripts re-ejecutables, y `outputSchema` provee resultados hijos estructurados autoritativos. Cada ejecución paga los costes de arranque del worker y de RPC por message-port, pero el arranque del host sigue sin bloquear, la cancelación puede terminar el worker y la serialización hace cumplir la frontera de valores. Los worker threads no son una frontera de seguridad. Las opciones inválidas fallan en lugar de degradarse al `null` de Claude Code; los consumidores retienen el control a través del handle de ejecución mientras los observadores reciben solo instantáneas. Los usuarios Web de nivel superior reciben también un registro de workflow durable y reproducible sin ensanchar el seam de ejecución ni acoplar la tarjeta original de herramienta a una UI específica de workflow.
