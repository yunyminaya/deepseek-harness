# Agent Note: El boot del config-tree de dsh web y la estratificación del transporte web

Status: implemented

[English](2026-07-24-web-config-tree-boot-and-transport-layering.md) | Español

> Alcance: cómo compone `dsh web` (cordis.yml + clases de boot pre-cordis + fuentes de configuración) y cómo se divide el transporte web entre paquetes (gateway / carrier / binding / grafo / recarga en desarrollo). La [nota de carga de plugins del cliente](2026-07-23-client-plugin-loading-model.es.md) posee la cadena de carga del lado del navegador que alimenta esta composición.

## Problema

`dsh web` era la única superficie ensamblada a mano que quedaba: `bootHost` montaba 32 plugins con configs fijadas en código (violando no-hardcoded-tunables), el roster del cliente era una constante de `web.ts`, y el TUI/headless llevaban tiempo siendo composiciones yml. La capa de transporte también tenía responsabilidades mal ubicadas: el webserver se autodescribía como un simple carrier y, sin embargo, conocía el grafo `__DSH_BOOT__`, poseía el canal SSE y fijaba en código el prefijo `/api/*`; el watch del bundle de desarrollo vivía dentro del registro de producción tras una bandera `watch?` sin propietario de ciclo de vida; el registro del grafo reescaneaba todo en cada emisión de `internal/plugin`; los errores por petición y los errores fatales del servidor compartían un único sumidero que siempre terminaba el proceso. Viajaba además un defecto visible para el usuario: la ruta web nunca cargaba `$DSH_HOME/.env`, de modo que `DSH_HOME=… dsh web` no podía encontrar una clave de API que viviera allí.

## Decisión

**La composición es un único árbol plano ensamblado.** `apps/cli/config/base.cordis.yml` más `apps/cli/config/web.cordis.yml` contienen todas las filas — el runtime del host (32 filas), la fila `api-gateway`, la fila `webserver` y las filas `dsh.client` (el roster del navegador; la fila de modules es a la vez una fila del host). Sin bundle troncal: cada plugin es una fila y cada campo de config es editable en yml. Esa postura se generalizó después a todo el repositorio, con las filas que ambas superficies comparten factorizadas en `apps/cli/config/base.cordis.yml` y cada superficie reducida a un overlay ([overlays de base compartida](../simplification/2026-07-29-shared-base-config-overlays.es.md)). La fila `dsh-client-hmr` es una fila de bundle ordinaria siempre activa (originalmente añadida en código por `--dev`; la bandera está retirada). El orden de las filas no tiene semántica de carga; la activación está impulsada por la disponibilidad de servicios. La auditoría compartida rechaza importaciones sin fibra, espera solo a las fibras fallidas para recuperar los errores de activación originales e informa de los servicios que dejan una fibra en `PENDING`; antes de lanzar, marca esas razones exactas de rechazo mediante un punto de control de proceso para que `installFailLoud` fusione la notificación duplicada del Loader mientras los rechazos no gestionados sin relación siguen siendo fatales. El artefacto app-boot de Node incrusta `@cordisjs/plugin-include` y deja `@cordisjs/plugin-loader` externo, de modo que el `EntryTree` del include y el host se enlazan a un único peer de Loader en lugar de dividir un árbol de config entre dos implementaciones de Loader.

**El pegamento de boot es un par de clases.** `AppCLIEntry` (apps/cli) y `AppWebEntry` (el kernel de la shell) contienen solo lo que debe existir independientemente de cordis: los hechos de argv, el conjunto de parches compuesto, el manifest de boot analizado, la instancia del sistema de módulos, los handles de la página de carga — todo lo demás vive en plugins. `AppCLIEntry.run()` tiene tres etapas: env en capas (ambient > `.env` de cwd > `$DSH_HOME/.env`, cerrando el defecto anterior) → composición de parches → boot include del Loader más la auditoría de activación. `AppWebEntry.run()` lo refleja en el lado del navegador: analiza `window.__DSH_BOOT__` en un `BootManifest` (dos vistas: filas de paquete npm para la tabla de módulos, filas de plugin cordis para la composición de entradas; un wire malformado lanza un error), construye el sistema de módulos, renderiza la página de carga, precarga el nivel `immediately` en paralelo con la preparación de Context/Loader, **espera a la precarga antes de crear las entradas** (la materialización es el require síncrono de `tree.import`, sin protección de espera de fibra inyectada; las aristas require entre paquetes como i18n → runtime/client necesitan que todas las fábricas del nivel immediately estén registradas primero — una carrera de arranque del 10–25% encontrada empíricamente en caso contrario), adopta la entrada de modules, crea las filas del grafo, settle, sweep.

**Cada fuente de configuración tiene un único lugar de declaración.** Los valores yml de los bundles son valores por defecto de ingeniería, las secciones de Settings son preferencias de usuario editables, las banderas de CLI se dirigen a las filas de su launcher propietario, y los valores de entorno entran mediante expresiones `!!js` de yml. Los parches sustituyen la config de una fila por completo. El `distIndex` frontal resuelto usa ese canal de parches como un hecho de ensamblaje. El valor por defecto de provider/modelo independiente del transporte pertenece a `ctx.agentDefaultModel`; el [punto de entrada directo headless](2026-08-09-headless-direct-core-entry-point.es.md) y el gateway Web consumen el mismo estado.

**El transporte se divide en cinco.** `dsh-host-apiproxy` es el plugin gateway (fila `api-gateway`): exporta por defecto `ApiProxyService`, configura solo `{nativeOpen?}`, consume el `ctx.agentDefaultModel` de la capa base neutro respecto al punto de entrada, provee `ctx.apiProxy`, permanece agnóstico al transporte y no registra rutas. `dsh-host-webserver` es un plugin simple de registro de rutas: `WebServer` provee `ctx.webServer` (`register(route) → disposer` con lanzamiento por patrón duplicado, renderizado de `renderIndex` — filas `webserver/index-inject` estructuradas y después transformaciones `tapIndex` raw en orden de registro — y `port`), escucha al activarse, responde a los fallos por petición con 400 y registro, y no conoce ningún concepto del harness. La mitad de nodo de conexión posee el binding `/api` desde `ctx.apiProxy` a través de `toFetchHandler`. La mitad de nodo de modules (`ClientModuleRegistry`, que provee `ctx.clientModules`) posee el escaneo incremental de paquetes, la ruta del bundle, las filas de inyección de boot y la notificación `onRebuilt`/`onGraphChanged`. La mitad de nodo hmr posee la recarga en desarrollo mediante la pertenencia a `fs.watchFile` y la ruta SSE `/plugins/events`.

**Disciplina de exportación de paquetes.** El paquete modules expone exactamente `.` (mitad de nodo) y `./client` (la mitad de navegador completa: `ClientModuleSystem`, `parseBootManifest`, la cara de plugin de adopción) — sin subrutas a medida; los tipos de wire se re-exportan a través de la raíz para los consumidores del lado del host. El apretón de manos de adopción: el kernel escribe la instancia construida en `window.__DSH_MODULES__` antes de que exista cordis; el apply de `./client` lee el slot (ausencia = error ruidoso) y provee `ctx.modules`.

## Consecuencias

- Recomponer un despliegue web es editar yml/parches; las piezas retiradas (`mountWebPlugins`, `CLIENT_PACKAGES`, `createHostWebPluginRegistry`, `startWebServer`, el conocimiento de grafo/SSE/api del webserver) se eliminan.
- [Headless es un punto de entrada directo al core](2026-08-09-headless-direct-core-entry-point.es.md): su profile de fábrica contiene las capacidades base compartidas del Agent y omite las capas Host, HTTP, Web y de navegador. La división del transporte de esta nota es el contrato de la superficie del navegador.
- Una trampa de TypeScript que conviene recordar: una aumentación `declare module 'cordis'` en un archivo **sin import de cordis** se degrada a una declaración de módulo independiente y rompe silenciosamente el merge de `Context` de todo el programa (`ctx.on`/`ctx.effect` desaparecen en todo el programa). Ancla con `import type {} from 'cordis'`.

## Alternativas consideradas

| Rechazada | Motivo en una línea |
|---|---|
| Paquete receptor dedicado `dsh-host-profile` | El estado del modelo de usuario pertenece al `ctx.agentDefaultModel` respaldado por Settings; un receptor Host extra duplicaría la propiedad y excluiría a los puntos de entrada directos |
| Plugin shim de ensamblaje en runtime que provee un servicio `apiHandler` | Existía solo porque `createApiProxy` vivía en runtime; moverlo a apiproxy hizo al gateway autosuficiente, y `toFetchHandler` es una función pura que invoca el lado del binding |
| Reescaneo completo + escaneo incremental coexistiendo | Dos implementaciones, dos semánticas; la ruta única por paquete cubre también el pase de activación |
| Una exportación `./impl` a medida en el paquete modules | Exportaciones no uniformes; el `./client` estándar lleva toda la mitad de navegador |
| dev overlay / `cordis.dev.yml` | Un solo yml; `!!js` no puede condicionar la existencia de filas, y `--dev` añadiendo una fila es toda la diferencia |
| Variables de entorno en la tabla de mapeo | El mismo campo tendría doble fuente env/json y habría que inventar una precedencia |
| create tras precarga sin barrera (dedup de `arrive()` como seguridad) | Refutado por una carrera de arranque del 10–25%: el dedup en vuelo cubre la doble obtención del mismo paquete, no las aristas require síncronas entre paquetes |
| Archivo json usado directamente como parches del loader | Las claves json se acoplarían a la estructura de filas yml; quienes escriben profiles necesitarían conocimientos de cordis |
