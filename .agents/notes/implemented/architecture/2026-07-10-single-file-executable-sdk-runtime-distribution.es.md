# Agent Note: Distribución del runtime del SDK como ejecutable de un solo archivo (single-exe)

Status: implemented

[English](2026-07-10-single-file-executable-sdk-runtime-distribution.md) | Español

## Problema

DeepSeek Harness necesita una forma de distribución dedicada del SDK para la biblioteca Python — sin instalación de Node, se ejecuta directamente en la plataforma objetivo: un ejecutable de un solo archivo (en adelante «el exe») que expone una interfaz de servicio JSON-RPC por stdio (`HarnessSdkJsonRpcServer`, el peer de la biblioteca Python), donde los plugins y la configuración realmente arrancados los decide por completo un `cordis.yml` suministrado desde fuera del exe.

- El protocolo JSONRPC para hablar con el SDK de Python ya está validado
- Se necesita una forma estandarizada de que `cordis.yml` cargue cada plugin (ESModule)
- La distribución debe llevar el runtime de Node y admitir un modo de depuración de código fuente enlazado localmente

## Decisión

### Ruta de empaquetado: el modo `--sea` de @yao-pkg/pkg

El exe se empaqueta con el **modo `--sea` (SEA mejorado)** de [@yao-pkg/pkg](https://github.com/yao-pkg/pkg) (el fork mantenido activamente después del archivado de vercel/pkg). En comparación con el SEA nativo de Node, pkg añade por encima un VFS `/snapshot` y hooks de módulo en runtime, entrega la entrada ESM al loader ESM por defecto de Node sin cambios y no depende de ninguna transcompilación ESM→CJS.
> Medido (macos-arm64, objetivo node24, pkg 6.21.0): pasan el import dinámico ESM con especificador simple dentro del VFS (incluido el top-level await), la interoperabilidad CJS, `node:sqlite`, el fallo ruidoso para nombres de paquete fuera del conjunto y el import ESM desde el disco fuera del VFS; `import.meta.url` llega sin cambios como `file:///snapshot/...`.

`--sea` exige objetivo ≥ node22; el exe apunta uniformemente a node24. Una invocación de pkg empaqueta exactamente un objetivo; las compilaciones multiplataforma la invocan una vez por plataforma.

Recordatorio de terminología: el VFS `/snapshot` de pkg no tiene nada que ver con la «instantánea» del sistema de pruebas de este repositorio (salidas esperadas de la repetición ACP, `$DSH_SNAPSHOT`); este documento dice «VFS» para el primero.

### La interfaz de servicio es un plugin: los dos paquetes sdk/server + examples/jsonrpc-demo

La implementación determinista del protocolo (`server.ts` / `transport.ts`) aterriza como dos paquetes siguiendo el patrón existente `acp/acp` + `examples/acp-demo` — la superficie de servicio es en sí misma un plugin:

- [`packages/sdk/server`](../../../../packages/sdk/server/README.md) (`@deepseek-ai/dsh-sdk-jsonrpc-server`): el plugin puro del protocolo; al aplicarse monta `HarnessSdkJsonRpcServer` más un transporte JSON-RPC delimitado por líneas en el stdio del proceso, con disposición mediante `ctx.effect()`. Si servir o no lo decide `cordis.yml`; un yml que no lo monta es un proceso legítimo que no sirve. La salida a nivel de protocolo pertenece al plugin (después de responder y vaciar la respuesta `shutdown`, dispone el runtime raíz para que la persistencia drene, y luego hace `exit(0)`; una descarga estilo HMR solo detiene el servicio sin salir del proceso).
- [`packages/examples/jsonrpc-demo`](../../../../packages/examples/jsonrpc-demo/README.es.md) (`@deepseek-ai/dsh-sdk-jsonrpc-demo`): un bin de aplicación delgado — `installFailLoud` + `loadEnv` + descubrimiento de configuración + `boot()` desde [`dsh-app-boot`](../../../../packages/boot/app-boot/src/index.ts), hecho una vez que el arranque se completa; el servidor lo levanta la entrada `dsh-sdk-jsonrpc-server` del yml. Su única dependencia es app-boot. La salida a nivel de proceso pertenece al bin (EOF de stdin/SIGTERM → disponer y luego 0, SIGINT → 130).

El descubrimiento de configuración tiene dos canales y falla ruidosamente cuando ambos faltan: primero la variable de entorno `DSH_CORDIS_CONFIG` (la convención del cliente SDK), después un argumento posicional de argv; ninguna ruta por defecto y ningún respaldo integrado de ningún tipo — «los plugins realmente arrancados los decide un cordis.yml externo» es una semántica dura.

### Resolución de plugins: el VFS contiene un árbol de paquetes real, el manifest de cierre ES la raíz de despliegue

Dentro del VFS del exe hay un **árbol de paquetes real en forma de artefacto de compilación** (el `lib/` de cada paquete más un `node_modules` real). La entrada JSON-RPC empaquetada suministra su base de harness instalada al Include raíz de app-boot: los especificadores de plugin relativos se resuelven desde el directorio de configuración externo, mientras que los nombres de paquete simples se resuelven desde el VFS, de modo que una configuración dentro de otro proyecto Node no puede ensombrecer el conjunto de plugins empaquetado. El bin de desarrollo ordinario deja los paquetes simples propiedad de la configuración. Los especificadores simples de la entrada empaquetada se resuelven hacia arriba a lo largo de `node_modules` desde la posición de la entrada dentro del VFS y aterrizan naturalmente dentro del VFS. El conjunto cerrado no necesita código de allowlist — el conjunto es lo que el VFS tiene instalado, e importar un nombre fuera del conjunto falla.

La raíz de despliegue es [`python/sdk-runtime/package.json`](../../../../python/sdk-runtime/package.json) (`dsh-jsonrpc-agent-pkg`, un miembro del workspace de pnpm y un manifest de dependencias puras sin código) — la fuente de verdad unificada para «qué plugins envía el exe» y «qué distribuye el runtime de Python». Añadir un plugin al exe = añadir una línea de dependencia al manifest y reempaquetar. [`scripts/verify-runtime-closure.ts`](../../../../scripts/verify-runtime-closure.ts) lee cada `apps/cli/config/agent-presets/*/agent.cordis.yml` enviado, evalúa las condiciones `disabled` que comparan `process.platform` para cada objetivo en `python/sdk-runtime/platforms.json`, y exige cada plugin de workspace activo en la raíz del runtime mediante una dependencia explícita `workspace:`. También recorre cada paquete de workspace cubierto por ese manifest y exige cada peer de workspace no opcional, informando de la cadena completa preset o paquete referenciador → dependencia ausente; las condiciones de plataforma desconocidas permanecen activas para que un plugin no pueda omitirse por una expresión no soportada. `pnpm run hygiene`, el estático de CI y la compilación del single-exe lo ejecutan antes de empaquetar. El despliegue también empaqueta según el `files` de cada paquete, de modo que los chunks compartidos que tsdown separa deben estar cubiertos por `files`.

La raíz de despliegue incluye `@deepseek-ai/dsh-mcp-client` como plugin de configuración personalizada explícitamente soportado aunque ningún preset enviado lo monte. Una configuración externa puede por tanto conectarse a servidores MCP stdio y Streamable HTTP suministrados por el usuario y registrar sus herramientas; la distribución no lleva esos servidores ni extiende el bridge a los Resources y Prompts de MCP. Los smokes del ejecutable y de la wheel instalada arrancan un servidor stdio temporal, descubren su herramienta y completan una llamada solicitada por el modelo.

### Pipeline de compilación y artefactos

[`scripts/build-exe-for-python-sdk.ts`](../../../../scripts/build-exe-for-python-sdk.ts): verificación del cierre del runtime → `pnpm run build` → (después de limpiar) `pnpm --filter dsh-jsonrpc-agent-pkg deploy --legacy --prod --config.node-linker=hoisted --config.auto-install-peers=false --config.link-workspace-packages=true` **directamente en** `python/sdk-runtime/src/deepseek_harness_runtime/runtime/node/` → restaurar cualquier paquete de workspace directo que el deploy legacy haya vuelto a subir bajo el `node_modules` del manifest fuente, omitiendo su árbol de dependencias local del paquete y rechazando cualquier vacío restante del manifest → reemplazar cada symlink de dependencia preparado por sus bytes objetivo, eliminar los enlaces `.bin` del gestor de paquetes y fallar si queda algún symlink → inyectar la configuración de pkg (`bin` apunta a `node_modules/@deepseek-ai/dsh-sdk-jsonrpc-demo/lib/packaged-bin.js` dentro del cierre, `assets` es un glob completo — el import dinámico es invisible al análisis estático de pkg, así que todo debe empaquetarse explícitamente) → preparar el addon objetivo `node-pty` → un `pkg --sea` por objetivo → los ejecutables `dsh-jsonrpc-agent-pkg-<platform>-<arch>` aterrizan en `dist-exe/` y se copian de vuelta al directorio del runtime. Las instalaciones de Linux compilan `pty.node` desde el código fuente; CI reconstruye ese addon dentro del contenedor manylinux 2.28 correspondiente antes de empaquetar, y el builder lo copia desde la instalación raíz al cierre preparado porque el deploy legacy omite ese directorio de efectos secundarios. Cada objetivo copia su binario nativo `@vscode/ripgrep` junto al ejecutable como el sidecar `-rg` requerido; los runtimes de pkg seleccionan ese sidecar mediante `process.pkg`, mientras que la ejecución ordinaria de Node usa `@vscode/ripgrep` directamente. macOS usa su prebuild de objetivo y también emite el `-spawn-helper` requerido. CI trata estos productos como entradas de prueba intermedias y conserva sus wheels de plataforma. Las cuatro banderas de deploy están fundamentadas en medición: `--legacy` es la ruta obligatoria con inject-workspace-packages desactivado; hoisted le da a pkg un layout estable de instancia única que la pasada de materialización explícita deja sin symlinks; desactivar la instalación automática de peers impide que los peers no declarados expandan el cierre; link-workspace-packages selecciona las dependencias directas del workspace. [`pnpm-workspace.yaml`](../../../../pnpm-workspace.yaml) sobrescribe las peticiones semver transitivas de `@deepseek-ai/cosmokit` y `@deepseek-ai/schemastery` a las fuentes de vendor fijadas, de modo que el deploy legacy nunca resuelve esos nombres no publicados desde un registro.

CI: [`.github/workflows/build-exe-for-python-sdk.yml`](../../../../.github/workflows/build-exe-for-python-sdk.yml), invocado para linux-x64 por la [validación requerida del pull request del runtime de Python](../testing/2026-08-12-required-python-runtime-pull-request-ci.es.md), disparado explícitamente por `workflow_dispatch` o la etiqueta `build-exe` para objetivos seleccionados, e invocado para todos los objetivos por el [flujo de publicación pública](../process/2026-08-11-python-publication-workflow.es.md). Las compilaciones nativas se ejecutan en linux-x64 / linux-arm64 (`ubuntu-24.04-arm`) / macos-arm64, con `~/.pkg-cache` en caché, y pkg gestiona la firma ad-hoc de macOS. Cada tramo conduce un modelo SSE mock a través del SDK con la configuración por defecto y un `cordis.yml` personalizado, conduce el exe directamente sobre JSON-RPC NDJSON, verifica el JSONL y la respuesta final, e instala wheels con forma de release en un venv limpio sin `runtime_bin`; Linux además inspecciona los requisitos GLIBC tanto del ejecutable como del addon nativo y se ejecuta en un contenedor manylinux 2.28, mientras que macOS verifica que el objetivo de despliegue del ejecutable encaja con la etiqueta de la wheel. Una ejecución completa de tres objetivos conserva cuatro artefactos, cada uno con un archivo de release: la wheel del SDK independiente de la plataforma y tres wheels nativas de runtime; un dispatch de subconjunto conserva la wheel del SDK y las wheels de runtime seleccionadas. Los ejecutables desnudos y los bundles de código fuente siguen siendo entradas de prueba intermedias. [`.gitlab-ci.yml`](../../../../.gitlab-ci.yml) acepta pipelines de tag `python-v<repository-version>` cuya versión coincide con el `package.json` raíz, compila una wheel del SDK y tres wheels nativas de runtime, y luego un único job serializado comprueba y publica las cuatro en el registro PyPI del proyecto. Windows es un no objetivo.

### Distribución del SDK de Python: dos portadores, exe para producción, node para desarrollo

El SDK de Python vive en [`python/`](../../../../python/README.md): `python/sdk` (el cliente) + `python/sdk-runtime` (el paquete portador del runtime). El directorio de datos del paquete de runtime contiene el `runtime/cordis.yml` por defecto incluido en el repositorio, el exe de plataforma inyectado por la compilación con su sidecar `-rg` requerido y el helper opcional de macOS, y el árbol de cierre `runtime/node/` inyectado por la compilación. La resolución automática de `resolve_bundled_launch_args()` **encuentra solo el exe**; el portador node se activa únicamente con un `DSH_RUNTIME_MODE=node` explícito (ejecutando `runtime/node/node_modules/@deepseek-ai/dsh-sdk-jsonrpc-demo/lib/packaged-bin.js`, que requiere un node de sistema ≥22.19), posicionado como el canal de verificación de desarrollo para los miembros de este repositorio, y no entra en las distribuciones de wheels.

[`scripts/build-python-release.py`](../../../../scripts/build-python-release.py) lee la versión autoritativa `X.Y.Z` o prerelease del `package.json` raíz del repositorio, convierte las prereleases a su grafía PEP 440 y prepara ambos paquetes en esa versión de wheel, con `deepseek-harness-sdk` dependiendo exactamente de la `deepseek-harness-runtime-bin` correspondiente. Un tag de release opcional `python-v<repository-version>` es una aserción de consistencia y se rechaza cuando difiere de la versión del repositorio; el centinela de desarrollo del `pyproject.toml` fuente nunca determina una versión de release. La preparación también lleva la licencia del repositorio a ambas wheels y los avisos de terceros a la wheel de runtime empaquetada. El SDK es una wheel `py3-none-any`; cada paquete de runtime solo-wheel contiene un exe y su sidecar `-rg` emparejado por arquitectura, y la wheel de macOS también contiene su helper de spawn emparejado por arquitectura. Las wheels de runtime usan una de `py3-none-manylinux_2_28_x86_64`, `py3-none-manylinux_2_28_aarch64` o la etiqueta conservadora `py3-none-macosx_14_0_arm64` para el objetivo de despliegue macOS 13.5 del ejecutable de Node 24; el hook de Hatch rechaza sdists, etiquetas universales, cargas útiles de plataforma mixta, sidecars ausentes o sobrantes y plataformas no soportadas.

La semántica dura del exe de «debe configurarse explícitamente» no cambia; la experiencia sin configuración la restaura el wrapper: cuando el llamador no dio ningún `cordis`, no nombró ningún runtime explícito y el entorno no tiene `DSH_CORDIS_CONFIG`, el cliente inyecta explícitamente el `cordis.yml` por defecto incluido en el repositorio (agent-core + llm-deepseek precargado + persistencia JSONL + bash-local + la entrada de servicio `dsh-sdk-jsonrpc-server`, con respaldos por variables de entorno `!!js`) mediante `DSH_CORDIS_CONFIG`.

### Linaje de nombres

`@deepseek-ai/dsh-sdk-jsonrpc-demo` (el paquete) → `dsh-jsonrpc-agent` (el bin) → `dsh-jsonrpc-agent-pkg` (el manifest de cierre; sin prefijo de scope, sorteando deliberadamente las reglas de forma de paquete de las restricciones para `@deepseek-ai/dsh-*`) → `dsh-jsonrpc-agent-pkg-<platform>-<arch>` (los artefactos exe). El `serverInfo.name` del cable sigue siendo `deepseek-harness-sdk-runtime` (un valor estable del protocolo); los nombres de la distribución Python son `deepseek-harness-sdk` / `deepseek-harness-runtime-bin`, mientras que los módulos de importación siguen siendo `deepseek_harness` / `deepseek_harness_runtime`.

## Disposición de los plugins tipo worker

`dsh-workflow-worker-thread` y `dsh-code-runtime-worker-thread` están soportados dentro del exe. Sus hosts compilados convierten la URL del `lib/worker.cjs` hermano con `fileURLToPath()` y pasan la cadena de sistema de archivos resultante a `Worker`, que es la forma que el hook de Worker de pkg resuelve dentro del VFS. Las entradas de worker son CommonJS porque ese hook compila los archivos de worker del VFS como CommonJS. El motor de workflow conserva su arranque por data-URL para la ejecución de código fuente sin compilar; solo su entrada hermana compilada usa la cadena de sistema de archivos. El smoke del ejecutable de configuración personalizada carga ambos backends, invoca una llamada real `run_code` y una llamada `workflow` sin agent, y exige que cada worker devuelva `42` desde dentro del VFS de pkg.

## Pruebas

La superficie de verificación tiene tres niveles. Nivel de mecanismo: las conclusiones medidas para la cadena `--sea` están incrustadas en las secciones de Decisión (import dinámico ESM dentro del VFS, instancia única de cordis, cadena de configuración de fallo ruidoso, `node:sqlite`, firma ad-hoc de macOS ejecutable). Nivel SDK: la suite pytest completa sin clave cubre el protocolo del cliente contra un peer de runtime falso, la limpieza de subprocesos, la propagación del cwd absoluto, el lanzamiento de doble portador y la resolución de portadores; CI raíz la ejecuta en Python 3.10. Nivel de extremo a extremo: cada compilación de plataforma completa un turno contra un endpoint mock a través de la ruta SDK por defecto, una configuración personalizada, la composición mínima independiente incluida en el repositorio y el protocolo binario directo, con el texto final y el JSONL comprobados. La ejecución mínima afirma su prompt de sistema exacto y su catálogo de dos herramientas, conserva el estado de Bash entre llamadas e invoca el editor. La configuración personalizada además conduce `run_code` y un `workflow` sin agent a través de sus archivos de worker reales dentro del VFS empaquetado. El escenario de búsqueda en el sistema de archivos exige que el modelo llame tanto a `glob` como a `grep` a través del sidecar `-rg` nativo del objetivo. El escenario MCP arranca un servidor stdio externo temporal, retrasa deliberadamente su respuesta inicial de `tools/list` e inicia inmediatamente después el primer prompt del SDK; el prompt debe ver y llamar a la herramienta descubierta, demostrando que `initialize` es un límite real de preparación por asentamiento del Loader, no un sleep de temporización. El mismo tramo de compilación ejecuta una instantánea específica del ejecutable incluida en el repositorio a través del SDK de Python: un modelo con guion sin clave monta un plugin de Cordis que registra una herramienta, invoca esa herramienta desde `run_code`, ejecuta un subagente spawn directo y un workflow que arranca un segundo hijo spawn, y desmonta después el plugin. El fixture desactiva explícitamente su Bash empaquetado no usado y el descubrimiento de skills locales para que su conjunto de herramientas no dependa del estado externo al repositorio, y la comparación normaliza los IDs opacos de mensaje, agent, ejecución de workflow y sesión a través del resultado del SDK y el flujo de notificaciones más los registros JSONL del padre y de los dos hijos. Este harness se mantiene separado del `pnpm run test:snapshot` de ACP porque los protocolos y los artefactos de compilación difieren. La wheel de plataforma se instala después en un venv limpio y se ejecuta sin `runtime_bin`.

Advertencia de conducción manual: el bin trata el EOF de stdin como «el cliente se ha ido» y dispone inmediatamente, de modo que un pipe de vida corta aborta un turno en vuelo — las ejecuciones impulsadas por pipe deben mantener stdin abierto hasta que el turno termine.

## Alternativas consideradas

**SEA nativo desnudo de Node.** El script principal inyectado debe ser un único archivo CJS, y el blob no lleva sistema de archivos ni resolución de módulos, así que un import dinámico de un especificador simple no tiene nada contra lo que resolver; la única opción es compilar los plugins estáticamente en el script principal y registrarlos a mano — evitando la resolución de módulos estándar y fijando el conjunto de plugins, en contra de «la configuración lo decide todo». La ruta final es de hecho «el fundamento SEA oficial + la capa de VFS/hooks de módulo de pkg»; lo rechazado es el uso desnudo, no el SEA en sí.

**Modo estándar de pkg.** Liquidado por la PoC, no un trade-off: convierte ESM en CJS + bytecode V8 mediante esbuild, la compilación vm del runtime no cablea ningún callback de import dinámico, cada `import()` lanza `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`, y `--options experimental-require-module` no tiene efecto; también depende de binarios de Node con parches de la comunidad (sin prebuild macos-arm64; compilar desde el código fuente sobre la marcha tarda unos 10 minutos). Viabilidad cero para la arquitectura de este repositorio.

**Preempaquetar cada paquete ESM→CJS en el VFS.** El compromiso que conserva la semántica real de resolución y solo degrada el formato de módulo; `--sea` pasó la medición directamente, así que esta capa de complejidad de compilación nunca hizo falta introducirla.

**jsonrpc-agent llevando las dependencias completas del cierre.** El bin de aplicación declararía 53+ dependencias que nunca importa — un «manifest de empaquetado» disfrazado de relaciones de dependencia reales — y obligaría a las restricciones a abrir dos excepciones para él, cordis-en-dependencias y un comodín de files. Con el manifest de cierre aterrizando en el paquete manifest del lado Python, las restricciones no necesitan ninguna excepción y el bin conserva la forma de paquete normal isomorfa a acp-agent.

**Un conjunto de plugins abierto (cargar plugins de usuario desde el disco).** El conjunto enviado es cerrado; la PoC confirmó de paso que el import ESM desde el disco fuera del VFS funciona (a través del canal de ruta relativa `ctx.baseUrl`). Está listado como evolución futura, que debe resolver por separado cómo compartir la instancia de cordis dentro del exe con los plugins externos.

## Consecuencias

**Comprado**: distribución de un solo archivo sin dependencias en las plataformas objetivo; semántica de plugins estrictamente idéntica a ejecutar desde el código fuente (el mismo árbol de paquetes real, sin transcompilación, sin registro); la interfaz de servicio, el conjunto de plugins y la configuración convergen en dos fuentes de verdad — `cordis.yml` más un manifest de dependencias; los portadores exe y node comparten un árbol y una semántica, de modo que la verificación de desarrollo nunca espera al empaquetado; los binarios oficiales de Node eliminan la preocupación de cadena de suministro de binarios con parches.

**Pagado**: artefactos del orden de 174MB con el código fuente entrando en el blob tal cual (sin ofuscación de bytecode; una distribución de código cerrado necesita una evaluación aparte); la capa de VFS/hooks de módulo de pkg sigue mantenida por la comunidad (el script de compilación fija `@yao-pkg/pkg@6.21.0`; actualizarla es un cambio explícito); `--sea` es una invocación por objetivo (coincidiendo con el tramo por plataforma de CI; las compilaciones locales multiplataforma son seriales).
