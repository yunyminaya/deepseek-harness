# Wheel del runtime de DeepSeek Harness

[English](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk-runtime/README.md) | Español

Paquete portador del runtime para el SDK de Python (dist `deepseek-harness-runtime-bin`, módulo `deepseek_harness_runtime`): localiza los binarios del runtime empaquetado que lanza el cliente `deepseek-harness-sdk` y distribuye la configuración predeterminada que sustenta las ejecuciones sin configuración (zero-config).

## Portadores del runtime

Dos portadores coexisten en `src/deepseek_harness_runtime/runtime/`; ambos los inyecta el build `scripts/build-exe-for-python-sdk.ts` del repositorio y ambos están ignorados por git:

- **exe (producción)** — un ejecutable de Node de un solo archivo `dsh-jsonrpc-agent-pkg-<platform>-<arch>` (plataforma: `linux`/`macos`; arquitectura: `x64`/`arm64`) con un sidecar `-rg` de ripgrep nativo del destino. Los builds de macOS también incluyen el hermano nativo `-spawn-helper` que `node-pty` usa allí. No se necesita ninguna instalación de Node en la máquina de destino. Es el único portador que se distribuye en los wheels; este paquete no publica sdists.
- **node (solo desarrollo)** — el closure de despliegue completo bajo `runtime/node/` (`package.json` + `node_modules/`), ejecutado como `node runtime/node/node_modules/@deepseek-ai/dsh-sdk-jsonrpc-demo/lib/packaged-bin.js` sobre un Node del sistema >= 22.19. Es el build desde el código fuente del checkout actual, pensado únicamente para el desarrollo y la verificación locales del repositorio; nunca se selecciona automáticamente y queda excluido de las distribuciones.

Ambos portadores contienen lo mismo, definido una sola vez: el [package.json](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk-runtime/package.json) de la raíz de este paquete es la raíz de despliegue del pipeline single-exe — un manifest (manifiesto) de dependencias puro, sin código propio, cuyo closure de dependencias ES a la vez el conjunto de plugins compilado en el exe y el árbol materializado en `runtime/node/`. Añadir un plugin a la distribución significa añadir una línea de dependencia allí y reconstruir.

El conjunto de plugins incluido contiene `@deepseek-ai/dsh-mcp-client`, de modo que una configuración Cordis externa puede conectarse a servidores MCP por stdio o Streamable HTTP y exponer sus herramientas al modelo. El wheel no incluye programas de servidor MCP ni credenciales: una configuración stdio aporta su ejecutable y sus argumentos, mientras que una configuración Streamable HTTP aporta su URL y sus cabeceras. El bridge soporta las herramientas MCP; los Resources y Prompts de MCP siguen sin soporte.

Si falta el exe, se lanza `FileNotFoundError` con ambas vías de obtención: compilar mediante `scripts/build-exe-for-python-sdk.ts` en un checkout de deepseek-harness, o instalar el wheel de runtime de la plataforma correspondiente producido por el flujo de trabajo de CI `build-exe-for-python-sdk`. Si falta el portador node de solo desarrollo, se nombra su única vía, el script de build. El flujo de trabajo conserva los wheels en lugar de archivos de ejecutable independientes. La estrategia de obtención está deliberadamente separada de la interfaz de búsqueda, de modo que una descarga bajo demanda pueda sustituirla más adelante sin tocar a los llamantes.

Cada wheel contiene exactamente un ejecutable de runtime y su sidecar `-rg` de ripgrep correspondiente. El wheel de macOS también contiene su helper de spawn nativo correspondiente; cualquier sidecar ausente deja esa instalación incompleta y es un error de arranque grave, incluso para una composición Cordis seleccionada que no use herramientas de búsqueda de archivos ni PTY. Los wheels de Linux no contienen helper de spawn porque `node-pty` usa directamente el addon `pty.node` incluido. Las etiquetas fijas son `py3-none-manylinux_2_28_x86_64`, `py3-none-manylinux_2_28_aarch64` y `py3-none-macosx_14_0_arm64`; la etiqueta de macOS coincide de forma conservadora con el objetivo de despliegue macOS 13.5 del ejecutable Node 24 incluido. El `platforms.json` de este paquete es dueño de los pares de etiqueta fija y nombre de ejecutable que usan tanto el builder de lanzamiento del repositorio como el hook de build aislado. El hook de build rechaza `py3-none-any`, los ejecutables de runtime ausentes o múltiples, los sidecars faltantes o sobrantes, los archivos no ejecutables y las etiquetas de plataforma no soportadas. El `package.json` de la raíz del repositorio aporta la versión compartida para este paquete y el SDK, y una etiqueta de lanzamiento `python-v<repository-version>` debe coincidir con ella.

## API de resolución

- `resolve_bundled_launch_args(mode=None) -> tuple[str, ...]` — la tupla argv que lanza el runtime empaquetado: `(exe_path,)` en modo exe, `(node_path, bin_js_path)` en modo node. Selección de modo: argumento explícito > variable de entorno `DSH_RUNTIME_MODE` (`exe` | `node`) > automático. La resolución automática encuentra SOLO el exe de producción — el portador node de solo desarrollo debe elegirse explícitamente, para que un despliegue de producción nunca pueda montarse en silencio sobre un build de código fuente.
- `bundled_runtime_path() -> Path` — la ruta del exe de la plataforma (solo portador exe); valida el sidecar `-rg` hermano obligatorio en todas las plataformas y el sidecar `-spawn-helper` en macOS. El portador node no tiene equivalente de ruta única y se lanza mediante la tupla argv anterior.
- `bundled_default_config_path() -> Path` — la configuración predeterminada incluida en el repositorio (ver más abajo).
- `bundled_package_dir() -> Path` — la raíz de datos del paquete instalado.

## Diseño zero-config

El binario del runtime siempre exige una configuración explícita (`$DSH_CORDIS_CONFIG`, o una ruta de configuración como argumento posicional de argv) y, sin ella, sale ruidosamente — esa semántica estricta forma parte del diseño del runtime y este paquete no la suaviza. El bin (`dsh-jsonrpc-agent`) arranca solo los plugins que lista la configuración; la interfaz de servicio (el servidor JSON-RPC por stdio) es en sí misma una de sus entradas (`@deepseek-ai/dsh-sdk-jsonrpc-server`) y, sin ella, el agent (agente) arrancado no tiene canal hacia el exterior. Este paquete incluye en el repositorio `runtime/cordis.yml` con la entrada de servicio JSON-RPC, el agent core, un adaptador DeepSeek precargado, persistencia JSONL, la política de checkpoints semánticos compuesta explícitamente, bash local y un provider de sistema de archivos local para la carga acotada de instrucciones del workspace. El backend de persistencia es dueño del almacenamiento duradero, mientras que la política independiente selecciona los checkpoints de petición, de despacho de herramientas y de paso completado. El adaptador lee `DEEPSEEK_API_KEY` y `DEEPSEEK_BASE_URL`; la persistencia, bash y el provider de sistema de archivos usan `DSH_SESSION_ROOT` y `DSH_CWD` con respaldos para las ejecuciones manuales. Cuando el llamante no usa ningún canal de configuración explícito, el cliente `deepseek_harness` inyecta la ruta de ese archivo mediante `DSH_CORDIS_CONFIG` (condiciones de inyección: [README del sdk](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk/README.md)). Zero-config es así una pasada de parámetros explícita y visible en el wrapper, no un respaldo oculto en el runtime.
